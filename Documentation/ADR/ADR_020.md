# ADR-0020: Capability inheritance from a scanned base class

**Status:** Accepted
**Date:** 2026-10-29
**Extends:** ADR-0009 (capabilities are derived from AST calls)
**Related:** ADR-0016 (control-only AST; class-A name heuristics removed), ADR-0019 (guardrail emission; a precedent for "a capability exists because the code shows it")

---

## Context

ADR-0009 derives a class's capabilities from the call sites in its own body. A class that calls `self.llm.invoke(...)` carries `calls_llm`; a class that does not has no `calls_llm`, whatever its name is and whatever its base does. After ADR-0016 removed the class-name heuristics, this became the only way a class could become an `agent`: the body shows the call, or the class is not an agent.

In practice, a project with a hierarchy —

```python
class BaseAgent:
    def __init__(self, llm_client):
        self.llm_client = llm_client
    async def _run_agent_loop(self, messages):
        return await self.llm_client.chat(messages)

class InvoiceAgent(BaseAgent):
    async def process(self, task):
        return await self._run_agent_loop(task)
```

— has a base class whose body carries the `calls_llm` call site, and subclasses whose bodies call only **methods of the base**. The subclass's own body has no LLM call. Under ADR-0009, `InvoiceAgent` has no capabilities, is classified as neither `agent` nor `llm_endpoint`, and disappears from the graph. The base's `calls_llm` is a fact the subclass *uses* — through inheritance — but ADR-0009 never said that fact could cross a class boundary.

This is not a hypothetical. It is the shape of the FinBot hierarchy (whose `BaseAgent` calls `self.llm_client.chat`), and it is the shape of every framework-agnostic agent base class that a project writes for itself. B.10a closed the *call-shape* gap (`self.llm_client.chat` now matches `CALLS_LLM_RULE`); B.10b closes the *inheritance* gap (a subclass uses the base's behaviour without re-declaring it).

This ADR decides the inheritance rule. It extends ADR-0009; it does not supersede it. A class with its own call site still gets its capabilities from ADR-0009. A class with none gets them, if its base has them, from this ADR.

---

## Decision

### 1. What inherits

A class's capabilities are `caps(own body) ∪ inherited_caps(base)`, where `base` is the class's **single base class**, resolved in the scanned tree. A class with no base, or with a base outside the scanned tree, inherits nothing.

`inherited_caps(base)` is the base's capabilities as computed by ADR-0009 (its own body's call sites), **not** the base's capabilities after *its* inheritance. Inheritance is **one level**: a class inherits from its direct base, not from its base's base. Transitive inheritance is not part of this ADR (§4).

The resolution is structural. `class InvoiceAgent(BaseAgent)` names `BaseAgent` in the `ClassDef.bases` list — an AST fact, not a name table. The name is resolved to a class the scan already parsed; a name that resolves to nothing (external base, typo, forward reference that never materialised) inherits nothing. This is the same "resolve against what the scan produced, do not guess" rule ADR-0016 applied to entry points, and the same reason: a name table of base classes would be a class-A heuristic in a new shape.

### 2. What does not inherit

- **A base outside the scanned tree** (`langchain.agents.AgentExecutor`, a `pip` package). It is not a class the scan parsed; the AST does not see its body; a `BaseAgent` in the project and an `AgentExecutor` in `langchain` are not the same fact. Framework detectors handle the framework's own base classes; this ADR handles project-local bases only.
- **A base's inherited capabilities.** Only `caps(own body)`, per §4 (one level).
- **A capability the base does not credit itself.** ADR-0009 is call-based; a base that declares `calls_llm` in a docstring but never calls an LLM has no `calls_llm`, and its subclasses inherit none.
- **A method's capabilities to a subclass's overriding method.** This is method-level inheritance, not class-level; it is not part of this ADR (§4).

### 3. What the rule does with an override

If a subclass overrides a method of its base, the subclass **still inherits** the base's capabilities. The AST sees the override (the same method name defined in the subclass's body), but it does not see whether the override calls the LLM — that is a per-method question, and method-level analysis is not part of this ADR.

The consequence is accepted: a subclass that overrides `_run_agent_loop` to something that does **not** call an LLM still inherits `calls_llm` from its base, and is classified as `agent`. This is a false positive at the level of *kind*, not at the level of *evaluation*: the class is a node in the graph — "an agent that has an LLM-calling method, inherited or otherwise" — and the Phase 3 LLM sees the actual chain and weighs it. A class whose base carries the LLM call is an agent by structure; the override is a runtime fact, and this ADR does not model runtime.

The alternative — refuse inheritance when an override is present — is rejected. It would turn the common shape (a subclass that overrides one method of an LLM-calling base, and calls the base's LLM-calling method from elsewhere) into a false negative, and the false negative is worse: it removes the node from the graph entirely, so no chain through it is enumerated, so no LLM ever sees it.

### 4. What is explicitly not done

- **Transitive inheritance** (A ← B ← C, where only C carries the call). One level only. Two levels is a graph traversal with a depth parameter, and the depth is a policy choice this ADR does not make. On the corpora this ADR was written against, one level covers the shapes; a corpus that needs two is a corpus that will argue for a second ADR.
- **Method-level inheritance** (a subclass method uses a base method's call site). This is a different relationship — it is about call sites, not about classes — and it needs per-method analysis the AST layer does not do (ADR-0001). It is a separate step, with a separate ADR.
- **Multiple inheritance.** A class with two bases inherits from neither in this ADR; the rule is single-base. Multiple inheritance is rare in the target code, and a "first base wins" or "union of bases" rule would be a decision about ambiguity this ADR does not have the data to make.
- **Declared capability.** A base that *says* it has a capability (a type, a docstring, a class attribute) but does not *call* it does not credit it, and its subclasses inherit nothing. ADR-0009 is call-based; this ADR does not widen it.
- **A base outside the scanned tree.** Framework bases are handled by framework detectors (ADR-0011), not by this ADR.

### 5. Cycle safety

If `A(B)` and `B(A)` (a forward reference that resolves both ways), the resolver must terminate and must credit each class at most once. The natural implementation — a visited set on the resolution chain, or a memoised `inherited_caps` keyed by class id — is required, not optional. A cycle is not a shape the target code should produce; it is a shape the resolver must survive.

## Rationale

### Why this is not a class-A heuristic

ADR-0016 decision 7 removed the heuristics that decided a class's *kind* from its *name*. This ADR decides a class's *capabilities* from its *base's capabilities* — a structural fact the AST sees (`ClassDef.bases`), resolved against the scan's own output, never against a table of names. A class named `BaseAgent` in `langchain` inherits nothing here; a class named `BaseAgent` in the project inherits what its body shows. The rule cannot be satisfied by naming a class `*Agent`; it can only be satisfied by writing a base that calls an LLM and a subclass that names it.

The distinction is the one ADR-0016 drew: a table that maps a name to a kind is a heuristic; an edge in the AST that names a class the scan already parsed is a fact. This ADR uses the second.

### Why one level, and not N

Two levels is a policy, not a fact: at depth 1 the rule is "a class inherits its base's own behaviour"; at depth 2 it is "a class inherits its base's base's behaviour", which is a different claim — a grandparent's behaviour reaches a grandchild only through the parent's use of it, and the parent may have replaced it. Depth 1 is the only depth at which the rule is unambiguous. Depth 2 needs a decision about what "uses" means when the parent overrides; that decision is method-level (§4), and this ADR does not make it.

A depth parameter would also make the resolver's cost a function of the parameter and the graph depth, and the target graphs have classes whose bases are external — the depth parameter would walk a chain of external bases whose bodies the scan never saw. Refusing to go past 1 keeps the rule structural.

### Why an override does not block inheritance

The AST sees the override; it does not see whether the override calls an LLM. That is a per-method fact, and per-method analysis is not part of this ADR. A rule that refuses inheritance on override would need the per-method fact to avoid a false negative — and without that fact, it would produce one systematically: the common shape is a subclass that overrides `_run_agent_loop` to add logging or error handling around the base's call, and calls the base's `_run_agent_loop` from its own body. The subclass is an agent, its body's `calls_llm` is real (inherited through the base's method, which the subclass invokes), and refusing inheritance would drop it from the graph.

The accepted false positive — a subclass whose override *replaces* the base's LLM call with something else — is a false positive on *kind*, and kind is a node property the Phase 3 LLM weighs. A false negative is a false negative on *enumeration*, and enumeration is the input to everything. The rule chooses the lesser.

### Why the base must be in the scanned tree

The AST cannot see a base it did not parse. A base outside the scan is a class whose body is not in the manifest; a rule that credited capability to a subclass of an unseen base would be guessing, and guessing in the capability direction is the shape ADR-0016 removed. Framework bases are handled by the framework detectors that parse the framework's own conventions (ADR-0011); this ADR is for the project's own bases.

### Why the resolution is not a name table

The name in `ClassDef.bases` is an identifier the code spells out. It resolves to a class the scan already produced — the same "resolve against what exists" rule that ADR-0016 decision 7 applied to entry points and ADR-0019 §1 applied to guardrails. A base class named `AgentBase` in the project inherits what its body shows; a base class named `AgentBase` in `langchain` inherits nothing, because `langchain.agents.AgentBase` is not a class the scan parsed. The name alone decides nothing.

## Consequences

- **A class with a scanned base inherits the base's capabilities**, one level, from `caps(own body)`. `class InvoiceAgent(BaseAgent)` where `BaseAgent`'s body calls `self.llm_client.chat(...)` carries `calls_llm`, is classified as `agent`, and appears in the graph.
- **A class whose base is external inherits nothing.** `class InvoiceAgent(langchain.agents.AgentExecutor)` is classified by the LangChain detector (ADR-0011), not by this rule.
- **A class that overrides a base method still inherits.** The override does not block; the false positive on kind is accepted and stated (§3).
- **Multiple inheritance is not supported.** A class with two bases inherits from neither. A project that needs multiple-inheritance inheritance argues for a second ADR.
- **A cycle terminates.** The resolver is required to be cycle-safe (§5).
- **`ADR-0009` is extended, not superseded.** A class with its own call site still gets its capabilities from ADR-0009. This ADR only fills the case ADR-0009 left empty: a class with no call site of its own, whose base has one.
- **B.10b implements this ADR.** The capability extractor resolves each class's `ClassDef.bases`, looks the name up in the manifest's parsed classes, and unions the base's own capabilities into the subclass's, one level, cycle-safe. No new edge kind, no new node kind, no new schema column. The `capability_extractor` is the only consumer, and `capability_extractor._classify_call` is unchanged — what changes is what a class's `SymbolCapabilities.capabilities` contains after extraction.
- **No change to `classification.py`.** It reads capabilities; a class with `calls_llm` is an `agent`, a class with `calls_llm | invokes_mcp_tool` is an `agent`, a class with `calls_llm` alone is an `agent` (per `AGENT_CAPABILITIES`, unchanged). This ADR changes *who has* `calls_llm`, not what `calls_llm` implies.

---

## Open questions this ADR does not resolve

1. **Transitive inheritance.** Not in scope. A future ADR.
2. **Method-level inheritance.** Not in scope. A future ADR, and it is a different kind of analysis (per-method call sites, not class-level bases).
3. **Multiple inheritance.** Not in scope. A future ADR, with a rule for what "single base" means when there are two.
4. **A base class the scan found but could not parse.** The resolver sees `BaseAgent` in `ClassDef.bases`, `BaseAgent` is a `ClassDef` the scan produced, but the file it came from had a syntax error, so the capability extractor did not credit it. The subclass inherits nothing — the base's capabilities are what the scan produced, and it produced none. This is consistent with the "resolve against what the scan produced" rule, and it is stated here so it is not a surprise.
