# ADR-0010: Multi-Chain Groups and Untrusted Channels

**Status:** Proposed
**Date:** 2026-10-12
**Context:** Phase 2+ — expanding the threat model

---

## Context

`find_chains` finds **linear chains** from `entry_point` to `sink`.
But indirect prompt injection does not work as a single chain:

**Scenario:**
1. Attacker **places** a document via `POST /upload` → RAG corpus.
2. User **triggers** processing via `POST /chat` → Agent →
   retrieve_docs → Agent → tool → sink.

**Each chain alone is not dangerous.** One is "file upload". The
other is "chat with agent". **Together** they implement indirect
prompt injection + RCE.

The reviewer said: "add untrusted sources to the graph."
The refinement: "add a **plane of analysis for groups of chains**
that meet through an untrusted channel."

---

## Decision

**Introduce `untrusted_source` as a new node kind, and
`find_chain_groups` as a new operation.**

### Naming

`untrusted_source` names the node — a channel through which
untrusted data passes. The same node **receives** writes (from
one chain) and **emits** reads (to another chain). It is a
single entity with two directions of flow.

The name reflects its role as "the origin of untrusted data for
the reading side". The writing side treats it as a target.

---

## Node Kind `untrusted_source`

| Type | Example | Source |
|---|---|---|
| `rag_corpus` | Vector database | RAG configs, framework detectors |
| `mcp_tool_description` | Tool description from MCP server | MCP SDK, `list_tools` |
| `email_inbox` | Incoming emails | Email client |
| `web_scrape_target` | External URL | `fetch` / `requests.get` calls |
| `user_upload` | Files from user | Upload routes |

**Key distinction:** `untrusted_source` is **not** `entry_point`.
`entry_point` is where a user sends a request. `untrusted_source`
is where untrusted data enters an agent's context.

---

## Chain Groups

**New operation:** `find_chain_groups(untrusted_sources, sinks)`.

**Algorithm:**

1. **Enumerate chains that WRITE to an untrusted source.**
   - `POST /upload → ... → rag_corpus:X`
2. **Enumerate chains that READ from an untrusted source.**
   - `rag_corpus:X → Agent → tool → sink`
3. **Group** chains by common `untrusted_source`.
4. **Check lethal trifecta** on the reading side.

**Result:** `ChainGroup` — a set of chains + common untrusted
source + lethal trifecta flag.

---

## Data Model

**New table `chain_groups`:**

```sql
CREATE TABLE chain_groups (
    id TEXT PRIMARY KEY,
    name TEXT,                          -- "RAG poisoning via /upload"
    untrusted_source_id TEXT NOT NULL,  -- node id
    write_chain_ids JSON NOT NULL,      -- chains that write
    read_chain_ids JSON NOT NULL,       -- chains that read
    lethal_trifecta INTEGER DEFAULT 0,
    verdict TEXT,                       -- exploitable / not_exploitable / uncertain
    confidence REAL,
    reasoning TEXT,
    validated INTEGER DEFAULT 0,
    priority TEXT,                      -- low / medium / high
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

---

## Combinatorial Explosion

Naive `find_chain_groups` is O(n²) and the LLM analysis cost
multiplies it. Approach: **fuzzing-style prioritization**.

1. **Cheap score** for each pair (regex / capability heuristic /
   small model). Low confidence, fast.
2. **Top-N pairs** → full LLM analysis.
3. **Then triples** (write + read + third element).
4. **Then quadruples**, and so on.

**Limits:**
- `max_groups` — hard cap on total groups.
- `max_pair_candidates` — cap on candidate pairs scored per run.
- `max_chain_length` — cap on individual chain length.
- `analysis_budget` — wall-clock or token budget.

**Progress feedback:**
- CLI must report progress and allow stop.
- Stage-by-stage: scoring → top-N analysis → triples.
Progress reporting, user stop, and directional scan control are 
backlog items. They are not in the first or second implementation 
queue.

See ADR-0012 (Chain group prioritization) for details.

---

## Consequences

### Positive

1. Indirect prompt injection is detected.
2. Multi-path attacks are visible.
3. Threat model is expanded beyond "HTTP → sink".

### Negative

1. `find_chain_groups` is a new complex operation.
2. May explode with n² groups — requires prioritization.

### Neutral

1. **Linear chains remain** — for direct attacks.
2. **Chain groups are an additional analysis plane.**

---

## Not in Scope

- Runtime verification (would require ADR-0013).
- Automatic discovery of untrusted sources without framework
  detectors (ADR-0011).

---

## Decision

**Add `untrusted_source` node kind and `find_chain_groups`
operation. Chain groups implement indirect prompt injection
detection. Combinatorial explosion is controlled by
fuzzing-style prioritization (ADR-0012).**
