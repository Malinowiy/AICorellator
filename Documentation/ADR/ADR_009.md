# ADR-0009: Capabilities on Nodes and Edges

**Status:** Accepted
**Date:** 2026-10-12
**Last reviewed:** 2026-10-20
**Context:** Phase 2+ — classification and edge semantics

---

## Context

Current classification and edge semantics are hardcoded for FinBot:

- Nodes have `kind` (8 types), classified by class names and suffixes (`*Agent`, `*Server`).
- Edges mean "can call" (`has_access_to`, `provides_tool`) — they do not distinguish read / write / exfiltration.
- Sinks are identified by method name (`execute_script`, `delete_file`).

Problems:

1. Obfuscation breaks name-based classification.
2. All chains look equally dangerous — 180 chains, all exploitable with confidence 0.85-0.95. No signal for prioritization.
3. The lethal trifecta (reads untrusted + has secrets + can exfiltrate) is not detected.

---

## Decision

**Introduce `capabilities` — a set of capabilities on nodes and edges.**

Capabilities are derived from AST calls, not from names. Not "class is named `*Sink`", but "class calls `subprocess.run`".

**Note on edges.** Edge capabilities describe *what a flow carries* (for example, that untrusted data may propagate). They are distinct from `flow_kind` (ADR-0015), which describes *what kind of flow an edge is* — control, data, or structural. An edge can have `flow_kind = "data"` and no edge capabilities (data flows, but its untrustedness is unknown), or `flow_kind = "data"` with `untrusted_propagates` (data flows and is untrusted). The two attributes are orthogonal.

---

## Capability Set

### Node capabilities

| Capability | Source | Meaning |
|---|---|---|
| `executes_code` | `subprocess.run`, `os.system`, `eval`, `exec` | Executes code |
| `executes_shell` | `subprocess.run(shell=True)`, `os.popen` | Executes shell commands |
| `reads_filesystem` | `open(path, 'r')`, `Path.read_text` | Reads files |
| `writes_filesystem` | `open(path, 'w')`, `Path.write_text` | Writes files |
| `reads_db` | `cursor.execute("SELECT ...")` | Reads database |
| `writes_db` | `cursor.execute("INSERT ...")` | Writes database |
| `http_egress` | `requests.post`, `httpx.post`, `aiohttp.post` | Sends data out |
| `http_ingress` | FastAPI routes, `request.body` | Receives data |
| `reads_env` | `os.environ`, `os.getenv` | Reads env vars |
| `reads_secrets` | `os.environ` + keys like `*_KEY`, `*_TOKEN` | Reads secrets |
| `calls_llm` | `openai.chat.completions`, `ollama.chat`, `ChatOpenAI` | Calls LLM |
| `invokes_mcp_tool` | MCP SDK, `session.call_tool` | Invokes MCP tool |
| `reads_untrusted` | untrusted input source (ADR-0010) | Reads untrusted data |

### Edge capabilities (transfer)

| Capability | Meaning |
|---|---|
| `data_flows_forward` | Data from source is passed to target |
| `control_flows_forward` | Control from source is passed to target |
| `untrusted_propagates` | Untrusted input may reach target |

**Relationship to `flow_kind` (ADR-0015).** `flow_kind` says whether the edge is a control edge, a data edge, or a structural edge. Edge capabilities describe properties of the flow: `data_flows_forward` is implied by `flow_kind = "data"`; `control_flows_forward` is implied by `flow_kind = "control"`; `untrusted_propagates` requires taint analysis (ADR-0010, not implemented). The edge capabilities are therefore a **superset** of the information in `flow_kind`, and the two are not redundant: `flow_kind` is the coarse classification, capabilities carry the fine-grained taint properties.

**Current implementation.** `flow_kind` is implemented (ADR-0015). Edge capabilities are **not** populated; the column exists, no producer writes to it. The only taint-adjacent attribute implemented today is `data_flow_confirmed` on `has_access_to` (ADR-0015), which describes the confidence of data-flow detection, not the untrustedness of the data.

---

## Capability Extraction

**Not full dataflow.** Extract the fact of a call from the AST body.

Example: a function body that calls `subprocess.run(cmd, shell=True)` receives the `executes_shell` capability.

False positives are accepted — they are better than no signal. The LLM in Phase 3 explains and prioritizes; it does not search.

---

## Lethal Trifecta Detection

A node with the capability combination:

`reads_untrusted` AND (`reads_secrets` OR `reads_env`)
AND (`http_egress` OR `writes_filesystem` OR `executes_shell`)

→ **Lethal trifecta.** Such nodes are prioritized.

A chain passing through a lethal trifecta node → `priority: high`.

**Status:** not implemented. The capability sets are defined in `patterns.py` (`LETHAL_TRIFECTA_READ_CAPS`, `LETHAL_TRIFECTA_SECRET_CAPS`, `LETHAL_TRIFECTA_EGRESS_CAPS`), but no code combines them into a node-level flag. `reads_untrusted` itself is now extracted (ADR-0010, 1.3a); the combination is backlog item 1.6.

---

## Schema Changes

The database is created fresh for each scan. Old databases are not migrated — they are discarded. `schema.sql` is the single source of truth.

Two changes to the schema:

- A `capabilities` column of type `JSON NOT NULL DEFAULT '[]'` is added to the `nodes` table.
- The same column is added to the `edges` table.
- An index is created on the JSON-extracted capabilities of nodes.

**Related schema change (ADR-0015).** The `edges` table also carries `flow_kind TEXT NOT NULL DEFAULT 'control'` and `data_flow_confirmed TEXT`. See ADR-0015 for the full specification.

**Lethal trifecta detection:** not implemented. Its read side is available (`reads_untrusted`, 1.3a); the combination code is backlog item 1.6.

**Edge capabilities:** `data_flows_forward`, `control_flows_forward`, `untrusted_propagates` are defined in the patterns registry but not populated. The schema has the column; no producer writes to it yet. Deferred to Phase 2. Note that `flow_kind` (ADR-0015) covers the coarse classification that `data_flows_forward` / `control_flows_forward` would carry; `untrusted_propagates` still requires taint analysis.

**Sink capabilities:** the set that makes a node a chain endpoint is now `patterns.SINK_CAPABILITIES` (see ADR-0014). It includes `http_egress` — a correction relative to the original ADR-0009 text, which listed exfiltration as a sink capability but did not include it in the classification set.

**Flow semantics:** `flow_kind` on edges is implemented (ADR-0015). Every stored edge carries `control`, `data`, or `structural`. `has_access_to` additionally carries `data_flow_confirmed` with one of six values describing the confidence of data-flow detection.

## Consequences

### Positive

1. Classification is more resistant to obfuscation.
2. Chain prioritization by capabilities, not "all exploitable".
3. Lethal trifecta is a deterministic signal (once `reads_untrusted` exists).
4. Opens the path to multi-chain analysis (ADR-0010).
5. `flow_kind` (ADR-0015) makes the coarse control-vs-data distinction explicit; capabilities carry fine-grained taint properties.

### Negative

1. Capability extraction is a new layer (~300-500 lines).
2. False positives are accepted — not eliminated.

### Neutral

1. `kind` remains, but becomes secondary to capabilities.
2. The LLM in Phase 3 uses capabilities for reasoning.
3. Edge capabilities and `flow_kind` are orthogonal: `flow_kind` is the coarse classification, capabilities are the fine-grained properties.

---

## Not in Scope

- Full dataflow analysis.
- Type-aware taint tracking.
- Inter-procedural analysis.

---

## Decision

**Capabilities are first-class attributes on nodes and edges.
They are derived from AST calls, not names. The lethal trifecta
combination flags high-priority chains. Schema is extended
without migration — the database is recreated per scan.**

**Edge capabilities are orthogonal to `flow_kind` (ADR-0015):
`flow_kind` is the coarse classification (control / data /
structural), capabilities are the fine-grained taint properties.
Both live on the same edge; neither replaces the other.**
