# ADR-0009: Capabilities on Nodes and Edges

**Status:** Accepted
**Date:** 2026-10-12
**Context:** Phase 2+ — classification and edge semantics

---

## Context

Current classification and edge semantics are hardcoded for FinBot:

- Nodes have `kind` (8 types), classified by class names and suffixes (`*Agent`, `*Server`).
- Edges mean "can call" (`has_access_to`, `provides_tool`) — they do not distinguish read / write / exfiltration.
- Sinks are identified by method name (`execute_script`, `delete_file`).

Problems:

1. Obfuscation breaks name-based classification.
2. All chains look equally dangerous — 180 chains, all exploitable with confidence 0.85-0.95. No signal for prioritization.
3. The lethal trifecta (reads untrusted + has secrets + can exfiltrate) is not detected.

---

## Decision

**Introduce `capabilities` — a set of capabilities on nodes and edges.**

Capabilities are derived from AST calls, not from names. Not "class is named `*Sink`", but "class calls `subprocess.run`".

---

## Capability Set

### Node capabilities

| Capability | Source | Meaning |
|---|---|---|
| `executes_code` | `subprocess.run`, `os.system`, `eval`, `exec` | Executes code |
| `executes_shell` | `subprocess.run(shell=True)`, `os.popen` | Executes shell commands |
| `reads_filesystem` | `open(path, 'r')`, `Path.read_text` | Reads files |
| `writes_filesystem` | `open(path, 'w')`, `Path.write_text` | Writes files |
| `reads_db` | `cursor.execute("SELECT ...")` | Reads database |
| `writes_db` | `cursor.execute("INSERT ...")` | Writes database |
| `http_egress` | `requests.post`, `httpx.post`, `aiohttp.post` | Sends data out |
| `http_ingress` | FastAPI routes, `request.body` | Receives data |
| `reads_env` | `os.environ`, `os.getenv` | Reads env vars |
| `reads_secrets` | `os.environ` + keys like `*_KEY`, `*_TOKEN` | Reads secrets |
| `calls_llm` | `openai.chat.completions`, `ollama.chat`, `ChatOpenAI` | Calls LLM |
| `invokes_mcp_tool` | MCP SDK, `session.call_tool` | Invokes MCP tool |
| `reads_untrusted` | untrusted input source (ADR-0010) | Reads untrusted data |

### Edge capabilities (transfer)

| Capability | Meaning |
|---|---|
| `data_flows_forward` | Data from source is passed to target |
| `control_flows_forward` | Control from source is passed to target |
| `untrusted_propagates` | Untrusted input may reach target |

---

## Capability Extraction

**Not full dataflow.** Extract the fact of a call from the AST body.

Example: a function body that calls `subprocess.run(cmd, shell=True)` receives the `executes_shell` capability.

False positives are accepted — they are better than no signal. The LLM in Phase 3 explains and prioritizes; it does not search.

---

## Lethal Trifecta Detection

A node with the capability combination:

`reads_untrusted` AND (`reads_secrets` OR `reads_env`)
AND (`http_egress` OR `writes_filesystem` OR `executes_shell`)

→ **Lethal trifecta.** Such nodes are prioritized.

A chain passing through a lethal trifecta node → `priority: high`.

---

## Schema Changes

The database is created fresh for each scan. Old databases are not migrated — they are discarded. `schema.sql` is the single source of truth.

Two changes to the schema:

- A `capabilities` column of type `JSON NOT NULL DEFAULT '[]'` is added to the `nodes` table.
- The same column is added to the `edges` table.
- An index is created on the JSON-extracted capabilities of nodes.

## Implementation Status

**As of 2026-10-13:**

| Capability | Extracted? | Notes |
|---|---|---|
| `executes_code` | Yes | pattern-based, from the capability registry |
| `executes_shell` | Yes | split into implicit (`os.system`) and explicit (`shell=True`) |
| `reads_filesystem` | Yes | includes mode-aware `open()` handling |
| `writes_filesystem` | Yes | |
| `reads_db` / `writes_db` | Yes | SQL keyword inspection on `cursor.execute` |
| `http_egress` | Yes | |
| `http_ingress` | No | listed for completeness; entry points are detected by kind, not capability |
| `reads_env` | Yes | |
| `reads_secrets` | Yes | substring match on env var names |
| `calls_llm` | Yes | |
| `invokes_mcp_tool` | Yes | |
| `reads_untrusted` | **No** | requires untrusted-source detection (ADR-0010, Phase 2) |

**Lethal trifecta detection:** not implemented. The capability combination is defined in the patterns registry, but no code combines them into a node-level flag. Deferred to ADR-0010 implementation.

**Edge capabilities:** `data_flows_forward`, `control_flows_forward`, `untrusted_propagates` are defined in the patterns registry but not populated. The schema has the column; no producer writes to it yet. Deferred to Phase 2.

**Sink capabilities:** the set that makes a node a chain endpoint is now the `SINK_CAPABILITIES` set in the patterns registry (see ADR-0014). It includes `http_egress` — a correction relative to the original ADR-0009 text, which listed exfiltration as a sink capability but did not include it in the classification set.

## Consequences

### Positive

1. Classification is more resistant to obfuscation.
2. Chain prioritization by capabilities, not "all exploitable".
3. Lethal trifecta is a deterministic signal.
4. Opens the path to multi-chain analysis (ADR-0010).

### Negative

1. Capability extraction is a new layer (~300-500 lines).
2. False positives are accepted — not eliminated.

### Neutral

1. `kind` remains, but becomes secondary to capabilities.
2. The LLM in Phase 3 uses capabilities for reasoning.

---

## Not in Scope

- Full dataflow analysis.
- Type-aware taint tracking.
- Inter-procedural analysis.

---

## Decision

**Capabilities are first-class attributes on nodes and edges.
They are derived from AST calls, not names. The lethal trifecta
combination flags high-priority chains. Schema is extended
without migration — the database is recreated per scan.**
