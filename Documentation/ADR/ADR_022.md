# ADR-0022: `source_type='user_upload'` end-to-end — a second producer

**Status:** Accepted
**Date:** 2026-10-30
**Related:** ADR-0009 (capabilities from AST calls), ADR-0010 (chain groups), ADR-0016 (control-only AST), ADR-0021 (store model; §10 `source_type` on the source), B.3b-user_upload-attribution

---

## Context

B.3b-user_upload-core shipped attribution: a read site in a writer's scope gets `source_type='user_upload'` on its `untrusted_source` node. The logic works (unit-tested), but it is inert end-to-end for two reasons, both recorded:

1. **No producer.** A filesystem read (`open('/uploads/x', 'rb')`) is not one of 1.3a's source types. `untrusted_sources.py` creates `untrusted_source` nodes only for the three 1.3a read shapes (`retriever.invoke`, `client.list_tools`, `imap.search`). An fs read produces no source node, so attribution has nothing to stamp.
2. **No `source_type` to overwrite.** Even if a source node existed, `untrusted_sources.py` sets `source_type` from the read shape's source type. `user_upload` is not a read shape; the attribution would need to either create a new node or extend a node's `source_type`.

The `user_upload` chain-group path is therefore empty on every corpus: the write side produces `writes_to entry_point → store` (B.3b-user_upload-*), the store has no `reads_from` because there is no `untrusted_source` to link to, and `find_chain_groups` pairs nothing.

The decision is: **how does a `user_upload` read site get a source node, and what is its `source_type`?**

---

## Decision

### 1. A second producer of `untrusted_source` for `fs` reads in a writer's scope

`untrusted_source` nodes are created by two producers, each keyed on its own evidence:

- **`untrusted_sources.py`** (1.3a) — the read **shape**: a call to a known source API (`retriever.invoke`, `client.list_tools`, `imap.search`). `source_type` = the source family.
- **`store/context/upload/attribution.py`** (this ADR) — a **write context**: an fs read site inside a writer's scope (the writer is an `UploadSite`; the read site's `source_file` is in the writer's scope: same file or shared import path). The source node is created **by the attribution pass**, with `source_type='user_upload'`.

The two producers are **disjoint by construction**: a read site that `untrusted_sources.py` already recognizes has a `source_type` from a known source family; a read site that `attribution.py` creates has no such recognition (an `open('/uploads/x', 'rb')` is not a `retriever.invoke`). A read site that both would recognize (impossible in 1.3a's rules: no source type calls `open`) is handled by precedence (§3).

### 2. The source node's identity

A `user_upload` source node is created from the read site's `(source_type='user_upload', call_target='<dotted open / aiofiles call>', source_file)`. The `untrusted_source_id` is the existing function's output. Two fs reads of the same file in the same file are one node (the identity is the call target and the file); two different files are two nodes. The store's `reads_from` link is to the source node, as in B.3c: one store, one or more sources.

The store the source reads from is the store the writer created (B.3b-user_upload-*): `store('fs', '<path prefix>')`. The read site's `identity_hint` (the `open` path's literal prefix) is what `reads_from`'s `identity_confidence` uses, as for any `fs` read (B.3b-fs).

### 3. Precedence

A read site that `untrusted_sources.py` already recognized keeps its `source_type`; the attribution pass **does not overwrite**. This is B.3b-user_upload-core's rule, unchanged. The new producer only creates nodes for read sites `untrusted_sources.py` did not (an `open` in a writer's scope). If a read site would produce both (a hypothetical future source type whose API is `open`), the first producer wins and the second is skipped; the state is documented, not silently merged.

### 4. What is not done

- **No `multi-role source_type`.** A source node has one `source_type`. A read site that is both a `user_upload` and a `rag_corpus` read (a corpus file read via `open` inside an upload handler's scope) is a **misclassification risk** the AST cannot resolve: `open` is not a source-type API, and `retriever.invoke` is. The attribution's scope rule (writer's `source_file` or shared import path) is what makes an `open` a `user_upload` read; a `retriever.invoke` in the same scope is still a `rag_corpus` source (precedence, §3). A node with two `source_type` values would need a value model the graph does not have; this ADR does not add one.
- **No `untrusted_source` for a read site outside the writer's scope.** An `open('/uploads/x', 'rb')` in a file the upload handler cannot reach (no same-file, no shared import) is not a `user_upload` read; no source node is created. The false negative is the same as B.3b-user_upload-core's attribution scope rule.
- **No `untrusted_source` for a write site.** The upload handler is the writer, not the reader. The writer's `writes_to` edge (B.3b-user_upload-*) is the write side; the attribution creates the read side.
- **No `untrusted_source` for an `open` without a literal path prefix.** If the read site's `open` path is a parameter (no literal prefix), the store identity is `None`; the source node's `identity_hint` is `None`; the `reads_from` link's `identity_confidence` is low (one-side literal), and the pair is weak (or absent — the resolver's `reads_from` emission follows B.3b-fs's rule: an unresolved identity produces no store, no link, no pair). Same as B.3b-fs.

### 5. The source node's shape

`kind='untrusted_source'`, `name='user_upload:<dotted call>'`, `attributes`: `source_type='user_upload'`, `call_target='<dotted call>'`, `source_file`, `line_start`, `reader_kind` (`'method'` / `'function'`), and, when available, `reader` / `reader_container` (the enclosing symbol, the same way 1.3a's sources carry it). No `parent_server` (that is a `mcp_tool_description` attribute). The `identity_hint` for the store link is the store's, not the source's (B.3b-fs's `literal_match` reads the store).

### 6. Where the producer runs

The attribution pass is already in the store resolver stage (stage 19, B.3b-user_upload-core) and is called with the writer sites and the delta. The new producer runs in the same stage, after the store's `writes_to` / `reads_from` are emitted: the attribution pass iterates the `fs` reads in the writer's scope, creates a source node per read site (if `untrusted_sources.py` did not already), and emits `reads_from` from the store to the source. The stage's order is unchanged: `StoreResolver.resolve` → `UserUploadContext.identify` → `find_upload_stores` → `attribute_source_type` (which now creates the sources and emits `reads_from`).

### 7. What changes in the graph

- **New `untrusted_source` nodes** for `fs` reads in a writer's scope (`source_type='user_upload'`).
- **New `reads_from` edges** from the writer's store to those sources, `structural`, `observed_by=["ast"]`, `data_flow_confirmed=NULL`, `identity_confidence` computed from §8 signals (the store's literal vs the read site's literal, plus code context; base 0.3, `fs`'s base — the attribution's base 0.5 is the **writer** side; the **reader** side is a plain `fs` read, base 0.3, same as `fs`).
- **`find_chain_groups`** joins `writes_to entry_point → store` with `reads_from store → source → has_access_to → reader → ... → sink` by store id. A `user_upload` group forms when the writer's store and the reader's store are the same (B.3b-user_upload-core's writer scope, plus the store's literal match).
- **No change** to `untrusted_sources.py`, `patterns.py`, `capability_extractor.py`, `classification.py`, the store families, the resolver, the confidence module, the prompt, the evaluator, the report.

---

## Rationale

### Why a second producer, not a multi-role `source_type`

A multi-role `source_type` (a list) is a value-model change that reaches the query layer (`find_chain_groups` reads `source_type`), the scoring (ADR-0012's `user_writable` / `user_readable`), and the prompt. It is the right answer only if a read site is genuinely both roles at once, and the AST has no such shape: an `open` is an fs read, a `retriever.invoke` is a corpus read, and a read site is one call. The two producers are disjoint; a second producer with its own source type is the simpler answer, and it keeps one `source_type` per node.

### Why the attribution pass, not `untrusted_sources.py`

`untrusted_sources.py` is a **shape** producer: it recognizes a call and names the source family. `user_upload` is not a shape; it is a **context** (an fs read in an upload handler's scope). The attribution pass already knows the context (it has the `UploadSite` and the writer's scope); making `untrusted_sources.py` context-aware would couple a shape detector to a context. The second producer keeps the shape detector shape-only and puts the context where the context lives.

### Why the store's writer scope decides, not the read site's file alone

The read site's file alone is not evidence of an upload: an `open('/uploads/x', 'rb')` in a config module reads a file that happens to live under `/uploads/`, but the module is not the upload's reader. The writer's scope (same file or shared import) is what makes the read site an upload reader. This is B.3b-user_upload-core's scope rule, applied to the read side. The false negative (a read site in a file the handler cannot reach) is accepted, same as the writer's.

### Why the reader's base is 0.3, not 0.5

The writer's base 0.5 (ADR-0021 §8 revision 2) reflects the upload context on the **writer** side. The **reader** is a plain fs read — the upload context is on the writer, not on the reader — and its base is the family's base (0.3). The pair's confidence is `min(writer_link, reader_link)`, which is `min(0.84 or 0.82 or 0.8, 0.3 + literal match + code context)`. For same-module with a literal match, the reader is `1 − 0.7·0.4·0.8 = 0.776`; the pair is `min(0.84, 0.776) = 0.776`. That is the honest number: the writer link is stronger than the reader link, and the pair is as strong as the weaker side (ADR-0021 §7).

### Why no `reads_from` without a store

The store is the place; the source is the read site; `reads_from` is the link. A store with no `writes_to` from a visible writer is not a store (B.3b-user_upload-core's §5); a source with no store is not a pair. The two are created together (the writer's store, the reader's source, the link), or not at all.

---

## Consequences

- **`source_type='user_upload'` is now produced end-to-end.** A read site in an upload writer's scope gets a source node with `user_upload`; the store's `reads_from` reaches it; `find_chain_groups` pairs it with the writer's write chain by store id.
- **The attribution pass creates nodes** in addition to stamping them. It runs in the store resolver stage (19); the stage's docstring says the stage creates nodes (B.3c's doc-debt corrected the C4 row; this ADR is the second reason).
- **`multi-role source_type` is not implemented.** A future ADR if a corpus argues for it; the misclassification risk (a `retriever.invoke` in an upload scope) is resolved by precedence (the shape producer wins).
- **The reader's base stays 0.3.** The writer's 0.5 is a writer-side signal; the pair is `min`, so the writer's strength does not raise the reader.
- **The false negatives are the same as B.3b-user_upload-core's:** a read site the writer cannot reach from its own file is not an upload read; an `open` with a non-literal path has no store, no link.
- **No change to `untrusted_sources.py`.** The shape producer stays shape-only; the context producer is the attribution pass.
