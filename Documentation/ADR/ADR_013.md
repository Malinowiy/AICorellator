# ADR-0013: Cross-File Edge Resolution

**Status:** Accepted
**Date:** 2026-10-13
**Last reviewed:** 2026-10-20
**Context:** Phase 1 — Parsing and normalization

---

## Context

Framework detectors (ADR-0011) are **per-file by design**. A detector receives one AST, one source file, and emits nodes and edges from that file alone. This is deliberate:

- A detector does not read other files, so it does not need import resolution.
- A detector does not maintain global state, so it is safe to run in parallel.
- A detector does not depend on manifest layout, so it works for any target structure.

This design has a blind spot: **cross-file edges are invisible to detectors**.

Three concrete cases from real targets:

**Case 1 — agent to tool across files (NMB, LangChain 1.0).**

The agent file imports a tools module and passes a tool list to a factory function. The tools module defines functions decorated as tools. The detector in the agent file sees the tool list by name only. It cannot resolve the name to the actual tool definitions in the tools module without reading that file. Result: no agent-to-tool edge.

**Case 2 — entry point to agent across files (NMB).**

The application file imports an agent factory and calls it inside a route handler. The agent factory is defined in a separate module and returns a compiled LangGraph agent. The entry-point detector in the application file sees a call to the factory and a method call on its result. It does not know that the factory returns an agent. Result: no entry-point-to-agent edge.

**Case 3 — MCP server to tool, no HTTP route (dvmcp, mcploitable).**

A framework-detected MCP server (`FastMCP(...)` or `Server(...)`) exposes tools through decorators. The server itself has no HTTP route, so the entry-point detector has nothing to attach to. Result: no starting point for chain enumeration, even though tools and sinks exist.

Without cross-file resolution, the NMB graph has 22 nodes and **0 edges**. With resolution, NMB has 26 nodes and 26 edges with 16 candidate chains; dvmcp has 30 nodes and 32 edges with 24 candidate chains.

---

## Considered Options

### Option A: Extend detectors to resolve imports

Teach each detector to read imported files, follow module paths, and resolve names.

**Rejected.** This breaks the per-file contract (ADR-0011). It requires each detector to duplicate import-resolution logic. It makes detectors stateful (they would need the manifest). It makes parallel execution unsafe. And it only solves the problem for one framework at a time — every new detector would need the same logic.

### Option B: Resolve cross-file edges in the normalizer

The normalizer (`ast_normalizer.normalize`) already receives the full manifest, all detector nodes, all entry points, and all TSA symbols. It is the natural place for cross-file resolution: it has the context, and it is already the component responsible for merging detector output into a single graph delta.

**Accepted.**

### Option C: Resolve cross-file edges in a dedicated module, called by the normalizer

Keep the normalizer focused on merging. Move the cross-file logic into a dedicated module under `framework_detectors/`, exposing one function. The normalizer calls it and appends the resulting edges.

**Accepted.** This is Option B, organized.

---

## Decision

**Adopt Option C.**

Cross-file edges are resolved in two places:

- A dedicated module (`cross_file.py`) for import-driven resolution.
- The normalizer itself for synthesis of virtual entry points and for reachability from any entry point to a sink.

Three resolvers are implemented.

**All resolvers populate `flow_kind` on the edges they create** (ADR-0015). An edge without `flow_kind` is a bug.

### Resolver 1 — agent to tool, via imports

Implemented in `framework_detectors/cross_file.py`.

This resolver links an agent node to tool nodes in modules it imports.

The algorithm:

1. Index tool nodes by source file from the detector result.
2. Index agents: nodes of kind `agent` with a `framework` attribute.
3. Collect per-file imports (`import X`, `from X import Y`, `from X import Y as Z`). Relative imports are skipped — resolving them requires a package root, which the manifest does not provide.
4. For each agent, for each imported module, find files whose path matches the module's dotted name. Matching is by trailing path segments: the module name `tools` matches `tools.py` and `pkg/tools.py`; the module name `mcp.servers.foo` matches `mcp/servers/foo.py`.
5. Emit `uses_tool` edges from the agent to **every** tool node in each matched file.

**`flow_kind`:** `control`. An agent calls a tool; whether data flows through the call is not analyzed (ADR-0015 — `data_flow_confirmed = "unknown"` for `uses_tool`).

**`data_flow_confirmed`:** `"unknown"`.

**Key design choice:** link to all tools in an imported module, not just the ones the agent references. This is a deliberate false-positive trade-off. ADR-0009 accepts false positives because Phase 3 (the LLM ensemble) filters them. Better a spurious edge than a missing one.

### Resolver 2 — entry point to agent, via the single-agent precondition

Implemented in `ast_normalizer._link_orphan_entry_points`.

This resolver links entry points with no outgoing delegation edge to the single framework agent in the project.

The algorithm:

1. Find agent nodes with a `framework` attribute. If there are zero or more than one, do nothing — the case is ambiguous.
2. Find entry-point nodes with no outgoing delegation edge.
3. Emit `delegates_to` edges from each orphan entry point to the single framework agent.

**`flow_kind`:** `control`. An entry point delegates to an agent; whether data flows through the delegation is not analyzed.

**`data_flow_confirmed`:** `"unknown"`.

**Key design choice:** the "single agent" precondition. In NMB, there is exactly one agent, and all routes go to it. This is a fact of the project, not a heuristic. When there are multiple agents, the case is ambiguous, and the resolver deliberately does nothing rather than guess.

### Resolver 3 — MCP entry synthesis

Implemented in `ast_normalizer._link_mcp_entries_to_tools`.

Framework-detected MCP servers have no HTTP route. To let chains start at MCP tools, the normalizer synthesizes one virtual entry point per framework-detected server, named `MCP:<server_name>`, and links it to every tool whose `parent_server` attribute matches.

The algorithm:

1. Index tools by `parent_server` attribute; only tools with framework provenance participate.
2. For each `mcp_server` node carrying a `framework` attribute, create a virtual `entry_point` node named `MCP:<server_name>`.
3. Emit `delegates_to` edges from the virtual entry to each tool whose `parent_server` matches.

**`flow_kind`:** `control`. An MCP client can invoke a tool; whether the tool description (which may be an untrusted source) reaches data into the call is not modeled here. That is the untrusted-source work (ADR-0010, backlog item 1.3).

**`data_flow_confirmed`:** `"unknown"`.

**Key design choice:** only framework-detected servers (those with a `framework` attribute) get virtual entries. Servers found via the file-path heuristic (`mcp/servers/*/server.py`) already carry `provides_tool` edges and are left alone. This keeps the two MCP discovery paths disjoint.

The synthesized entry point carries `entry_kind = "mcp"` so downstream components can distinguish MCP entries from HTTP routes.

### Cross-file reachability from entry points to sinks

Implemented in `ast_normalizer._link_entry_points_to_sinks`, supported by a per-file call graph collected in `entry_points.py`.

This resolver links any entry point — HTTP route, synthesized MCP entry, CLI script, Streamlit app — to a sink that is reachable through same-file calls.

The algorithm:

1. For each entry point, BFS from the handler (or module for module-level entries) through the file's call graph.
2. Collect the set of reachable function names.
3. For each sink node in the same file whose name is reachable, emit a `has_access_to` edge.

**`flow_kind`:** `data` if `data_flow_confirmed` is one of `parameter_match`, `local_var_match`, `call_result_match`; otherwise `control`. The `data_flow_confirmed` value is computed by the argument analysis in ADR-0015.

**`data_flow_confirmed`:** computed from the arguments of the sink call in the entry-point handler's body, per ADR-0015. If the sink call is in a different function (transitive reachability), `data_flow_confirmed = "unknown"` — the analyzer does not follow arguments across function boundaries.

**Key design choice:** the call graph is name-keyed, records only `ast.Name` calls (not attribute calls), and is **control-flow reachability**, not dataflow. ADR-0001 forbids full dataflow; control-flow reachability is in scope. ADR-0009 accepts false positives.

### New edge kind: `uses_tool`

The stored edge kinds were: `uses_model`, `provides_tool`, `delegates_to`, `has_access_to`, `guards`.

`uses_tool` is added as a sixth stored kind. It represents "an agent calls a tool" — distinct from `has_access_to` ("a tool reaches a sink") and `provides_tool` ("an MCP server exposes a tool").

`uses_tool` is added to three places:

- The valid edge kinds set in the graph models module.
- The `CHECK` constraint on `edges.kind` in the schema.
- The edge kinds registry in the patterns module.

**`flow_kind` for `uses_tool`:** `control`, per ADR-0015.

### Edge merge and ID remap

When a detector node replaces a TSA node with the same name and source file, the normalizer records an ID remap from the removed node to the replacement. Edges that referenced the removed node are re-pointed to the replacement, and edge IDs are recomputed and deduplicated.

Without this, cross-file edges built **before** the detector merge would be silently dropped. This was a real bug: delegation edges from entry points to TSA-classified agents disappeared as soon as the detector created a node with the same name.

**`flow_kind` is preserved across the merge.** The re-pointed edge keeps its original `flow_kind` and `data_flow_confirmed`.

---

## Rationale

- **Per-file detectors stay per-file.** ADR-0011's design is preserved. Cross-file resolution is a normalizer concern, not a detector concern.
- **False positives are acceptable.** ADR-0009 already establishes this. The resolvers link to all tools in an imported module and link all orphan entry points to the single framework agent. The LLM ensemble in Phase 3 filters. A missed edge is worse than a spurious one, because a missed edge breaks a chain.
- **No import graph, no interprocedural dataflow.** The resolvers use trailing-segment matching on module paths, a single "framework agents count equals one" check, and a same-file call graph. They do not build a project-wide call graph or perform dataflow analysis.
- **`flow_kind` is mandatory.** Every cross-file edge carries it (ADR-0015). An edge without `flow_kind` is a construction bug, caught by tests.
- **The result is measurable.** On NMB: 0 edges became 17 edges; 0 chains became 8 chains. On mcploitable: 0 chains became 5. On dvmcp: 0 chains became 24. On FinBot: no change (91 edges, 180 chains). The P0/P2 and CLI/Streamlit work moved these numbers further; see the current status in `README.md`.

## Consequences

### Positive

1. LangChain 1.0 projects, where agents are created through factories, produce a usable graph.
2. MCP servers, which have no HTTP route, produce chains through synthesized entries.
3. The per-file detector contract (ADR-0011) is preserved.
4. Cross-file logic is isolated in one module plus three small normalizer helpers.
5. The edge merge fix makes the normalizer correct for any detector, not just LangChain.
6. `flow_kind` on every cross-file edge gives the LLM the control-vs-data distinction it needs (ADR-0015).
7. New detectors — OpenAI Agents SDK, future MCP SDKs — inherit cross-file resolution and MCP entry synthesis for free.

### Negative

1. False positives: an agent that imports a module with 20 tools gets edges to all 20, even if it uses only 3. Accepted (ADR-0009).
2. Relative imports are not resolved. Accepted; relative imports are rare in agent code, and resolving them requires package-root information.
3. The single-agent heuristic does not scale to multi-agent projects. Accepted for now; multi-agent resolution is a separate problem.
4. Call-graph reachability is intra-file. A tool that reaches a sink through another module is not linked. Deferred.

### Neutral

1. `uses_tool` is a new stored edge kind. The database is recreated per scan (ADR-0003), so no migration is required.
2. Edge ID remap during merge is a small, local change to the normalizer.
3. MCP entries are marked with `entry_kind = "mcp"`; HTTP routes remain unmarked.
4. `flow_kind` is a new mandatory attribute on edges (ADR-0015).

---

## Deferred

1. **Transitive import resolution.** If one module imports a second, and the second imports a third, Resolver 1 does not follow the chain. Accepted; not needed for current targets.
2. **Per-name resolution.** Resolving a tool list to exactly the functions it contains, not all tools in the module. This is the precision upgrade for a future iteration.
3. **Relative imports.** Requires package-root inference. Deferred.
4. **Multi-agent routing.** Linking each entry point to the specific agent it calls, when there are multiple agents. Deferred; needs per-route dataflow.
5. **Cross-file edges for other edge kinds.** Currently agent-to-tool, entry-to-agent, MCP-entry-to-tool, and entry-to-sink. Agent-to-model and MCP-server-to-tool via the path heuristic are still built per-file.
6. **Cross-file tool to sink.** A tool that calls a sink in another module is not linked to that sink. Same-file reachability (implemented) covers the common case; cross-file requires an extension to the call graph that spans imports. Deferred (backlog item "Cross-file tool → sink"). When implemented, the resolver must populate `flow_kind` and `data_flow_confirmed` (ADR-0015).
7. **Cross-file data-flow analysis.** Even when the cross-file `has_access_to` is built, `data_flow_confirmed` will be `"unknown"` unless the argument analysis can see across the call boundary. Full cross-file data flow is out of scope (ADR-0001).

## Decision

1. Cross-file edges are resolved by the normalizer, not by detectors.
2. Three resolvers: `resolve_agent_tool_edges` (agent to tool via imports), `_link_orphan_entry_points` (entry point to single framework agent), and MCP entry synthesis (`mcp_server` to virtual `entry_point` to tool).
3. Cross-file reachability from entry points to sinks is implemented via a per-file call graph collected in `entry_points.py` and consumed by `_link_entry_points_to_sinks`.
4. `uses_tool` becomes a sixth stored edge kind.
5. Edge ID remap during detector-node merge prevents silent edge loss. `flow_kind` is preserved across the merge.
6. False positives are accepted (ADR-0009).
7. Every cross-file edge carries `flow_kind` (ADR-0015). Edges created by Resolvers 1 and 2, and by MCP entry synthesis, carry `flow_kind = "control"`. Edges created by the entry-to-sink resolver carry `flow_kind = "data"` when `data_flow_confirmed` is one of the three data values, otherwise `control`.
