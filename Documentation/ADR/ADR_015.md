# ADR-0015: Control Flow vs Data Flow in the Graph

**Status:** Proposed
**Date:** 2026-10-20
**Context:** Phase 1 — Graph model, Phase 3 — Chain evaluation

---

## Context

The graph currently has one class of edges — `has_access_to`, `uses_tool`, `uses_model`, `delegates_to` — that mixes two semantically different things:

- **Control flow** — "X calls Y" (or "X can reach Y through calls").
- **Data flow** — "data from X reaches Y".

An LLM evaluating a chain cannot distinguish these two. It sees `has_access_to` between `search_files` and `delete_file` and reads it as "data from `search_files` reaches `delete_file`" — even though the edge only means "both are declared in the same MCP server". On FinBot, this produces ~160 false positives out of 180 chains (see `Documentation/Analysis/FP_TP_analysis.md`).

The root cause is structural: the graph does not encode what kind of flow an edge represents. No prompt can fix this — the information is missing from the payload the LLM receives.

Two additional facts shape the decision:

- **Data flow cannot be detected reliably at the AST level.** Name-based argument analysis finds `os.remove(query)` where `query` is a tool parameter. It does not find `os.remove(config.get("path"))` or `os.remove(f"{base}/{name}")`. False negatives are guaranteed.
- **Chain groups (ADR-0010) need partial chains.** Real multi-step attacks connect through an untrusted source: one chain writes, another reads. If chains with only control edges are filtered out, chain groups have no material to work with.

Therefore the goal is not to remove control-only chains, but to **mark each edge with its flow kind** and let the LLM use that signal for calibration. The graph stays complete; the information becomes explicit.

---

## Considered Options

### Option A: Add `data_flow_confirmed` only to `has_access_to`

Mark the one ambiguous edge kind. Leave the rest as they are.

**Rejected.** `uses_model`, `uses_tool`, `delegates_to` can also carry data (an agent passes a user-supplied argument to a tool; a route handler passes a request to an agent). Marking only `has_access_to` makes `flow_kind` a special case rather than a property of every edge. It also blocks future enrichment: when a framework detector learns to analyze an agent's arguments, there is no field to record the result.

### Option B: Split `has_access_to` into `calls` and `data_flows_to`

Two edge kinds, both built. The LLM sees the difference directly.

**Rejected.** This doubles the edge count for the same relationship, densifies the graph before taint is in place, and breaks `find_chains` (which would see two paths where one exists). Colocation — two tools declared on the same MCP server but not calling each other — would either produce no edge (breaking chain groups) or produce both kinds (ambiguous). A single edge with a `flow_kind` attribute is simpler and does not lose information.

### Option C: `flow_kind` on all edges, plus `data_flow_confirmed` on `has_access_to`

Every edge carries `flow_kind`: `control` | `data` | `structural`. `has_access_to` additionally carries `data_flow_confirmed`, a six-valued field describing how confidently data flow was established.

**Accepted.**

---

## Decision

**Adopt Option C.**

### `flow_kind` on all edges

Every stored edge carries a `flow_kind` attribute with one of three values:

| `flow_kind` | Meaning | Edge kinds |
|---|---|---|
| `control` | X calls Y, or X can reach Y through calls. Data flow not confirmed. | `uses_model`, `uses_tool`, `provides_tool`, `delegates_to`, `writes_to`, `has_access_to` (default) |
| `data` | Data from X reaches Y, confirmed by argument analysis. | `has_access_to` (when analysis succeeds) |
| `structural` | X and Y are related declaratively, not through execution. | `guards` |

**Structural edges do not participate in chain enumeration.** `guards` says "this guardrail protects this component" — a defensive control, not a step in an attack path. `find_chains` traverses only `control` and `data` edges.

**`provides_tool` is control.** "This MCP server exposes this tool" is a declaration only if the analysis assumes the tool is never called. See *`provides_tool` is control, not structural* below.

### `data_flow_confirmed` on `has_access_to`

When building a `has_access_to` edge, the normalizer analyzes the arguments of the sink call inside the tool body and records one of six values:

| Value | Meaning | `flow_kind` |
|---|---|---|
| `parameter_match` | A sink argument is a parameter of the tool itself (`def tool(query): os.remove(query)`) | `data` |
| `local_var_match` | A sink argument is a local variable derived from a tool parameter (`x = query.strip(); os.remove(x)`) | `data` |
| `call_result_match` | A sink argument is the result of another call (`os.remove(parse(query))`) | `data` |
| `literal_only` | All sink arguments are literals or constants (`os.remove("/tmp/x")`) | `control` |
| `no_args` | The sink is called with no arguments | `control` |
| `unknown` | Arguments could not be analyzed (`os.remove(config["path"])`, attribute access, unpacking) | `control` |

**Analysis is name-based, not value-based.** The analyzer does not track data through function calls, dictionary lookups, or f-strings. It matches names: a tool parameter name against a sink argument name; a local assignment target against a sink argument name; a call target against a sink argument. Anything else is `unknown`.

**False negatives are accepted.** `call_result_match` is recorded when a sink argument is the result of a call, but the analyzer does not know what that call returns. It is treated as `data` because the pattern suggests flow; if the call actually returns a constant, this is a false positive on the edge — accepted (ADR-0009).

### `uses_model`, `uses_tool`, `delegates_to`

These edges carry `flow_kind = "control"` and `data_flow_confirmed = "unknown"`.

**Rationale:** the analyzer does not see the body of an agent. An `AgentExecutor` is a LangChain object, not a function whose arguments can be matched. An agent may pass a user-supplied argument to a tool, but the graph cannot establish this without analyzing the agent's body — which the framework detectors do not do today.

**This is an enrichment point, not a permanent limitation.** Each framework detector may, in a future iteration, analyze its own framework's argument-passing patterns and upgrade the `data_flow_confirmed` value on the edges it owns. The schema and the model support this without change. The LangChain detector, for example, could inspect a `create_agent(tools=[...])` call and see whether a tool is invoked with a parameter derived from the agent's input.

### `provides_tool` is control, not structural

`provides_tool` carries `flow_kind = "control"` and `data_flow_confirmed = "unknown"`.

**The access path is the attack path.** `provides_tool` says "this MCP server exposes this tool". Read literally, that is a declaration: the tool exists and a client may call it. From an attack-path standpoint the distinction does not survive. An agent that can reach a server exposing `delete_file` has `delete_file` in its reachable action set; whether a particular request invokes it is a runtime question, not a structural one. Classifying the edge as a declaration would remove from chain enumeration the very step an attacker uses — the move from agent to dangerous tool.

**Conservative by construction.** The graph prefers a spurious edge over a missing one (ADR-0009, ADR-0013). Treating `provides_tool` as a declaration would hide reachable dangerous actions whenever invocation is indirect: dispatched by the MCP framework, selected by the model, or triggered by a prompt. Those are precisely the cases worth evaluating.

**`guards` remains structural.** A guardrail is a defensive control, not a step in an attack path. "This hook guards this action" describes protection, not execution: neither data nor control flows from the guardrail to the guarded component along that edge. Traversing it would invent a step that does not exist.

### Attribute structure

On the `edges` table:

- `flow_kind TEXT NOT NULL DEFAULT 'control'` with `CHECK (flow_kind IN ('control', 'data', 'structural'))`.
- `data_flow_confirmed TEXT` (nullable) with `CHECK (data_flow_confirmed IS NULL OR data_flow_confirmed IN ('parameter_match', 'local_var_match', 'call_result_match', 'literal_only', 'no_args', 'unknown'))`.

`data_flow_confirmed` is populated only for `has_access_to`. For every other edge kind it is `NULL`.

### `data_edges_only` parameter

`find_chains` gains a `data_edges_only: bool = False` parameter.

- `False` (default) — all chains, with `flow_kind` present on every edge. The LLM decides how to weigh `control` vs `data`.
- `True` — only chains where at least one edge has `flow_kind = "data"`.

The parameter is a filter for analysts who want a high-precision shortlist. It is not the default, because it removes partial chains that chain groups will need.

Structural edges never participate, regardless of the parameter.

### Phase 3 prompt

The prompt payload for each edge gains `flow_kind`, and for `has_access_to` also `data_flow_confirmed`. The prompt instructs the LLM that:

- A chain with `data` edges is stronger evidence than a chain with only `control` edges.
- A chain with `structural` edges on its path is a construction error and should be reported as such.
- The presence or absence of data flow is a signal, not a verdict. The LLM decides confidence.

**No hard calibration rules** (such as "control only → confidence ≤ 0.5") are imposed. The LLM receives the signal and reasons about it, exactly as it reasons about other structural properties.

### Enrichment principle

`data_flow_confirmed` is an **enrichable** attribute. Each framework detector may upgrade it for the edges it owns, using framework-specific knowledge that a generic AST analyzer does not have. The schema and model support this from day one. An `unknown` value means "not analyzed by a component that knows the framework", not "permanently unknown".

---

## Rationale

- **Information, not filtering.** The LLM receives `flow_kind` and `data_flow_confirmed` on every edge. The graph stays complete. Chains with control-only edges remain available for chain groups, for manual review, and for the LLM to reason about when other structural signals are strong.
- **False negatives are not fatal.** Because control-only chains are not removed, a missed data-flow detection lowers confidence but does not delete the chain. An analyst can still investigate.
- **Chain groups keep their material.** `find_chain_groups` connects chains through an untrusted source. Intermediate control edges are a valid part of a group; only the write side and the read side need `data` edges. Filtering out control chains now would leave nothing for chain groups later.
- **`flow_kind` is orthogonal to LLM confidence.** The LLM sets confidence; `flow_kind` is an input, not a rule. The prompt informs, the model decides.
- **Extensible.** New edge kinds declare their `flow_kind` at creation. Framework detectors can upgrade `data_flow_confirmed` without schema changes.

## Consequences

### Positive

1. The LLM can distinguish "X calls Y" from "data from X reaches Y". The FinBot false-positive root cause is addressed at the model level.
2. Control-only chains survive and feed chain groups.
3. `data_edges_only` gives analysts a high-precision shortlist when they want one.
4. Framework detectors have a documented place to add framework-specific data-flow analysis.
5. The graph is more informative without being denser — no new edge kinds, no duplicate edges.

### Negative

1. `data_flow_confirmed` is unreliable. Name-based matching misses indirect flows and cannot track values. Accepted; the alternative is full dataflow analysis (ADR-0001, out of scope).
2. `uses_model`, `uses_tool`, `delegates_to` carry `data_flow_confirmed = "unknown"`. Until framework detectors enrich them, data flow through agents is invisible. This is a known gap, not a permanent limitation.
3. The normalizer gains a new analysis pass (argument matching against sink calls). It is local and cheap but requires tests.

### Neutral

1. The database is recreated per scan (ADR-0003), so no migrations are required.
2. `has_access_to` remains a single edge kind; its `flow_kind` and `data_flow_confirmed` describe the flow, not the kind.
3. `structural` edges (`guards`) are excluded from `find_chains`. This is a semantic rule, not a filter option. `provides_tool` is control, so MCP access paths stay enumerable.

## Deferred

1. **Taint sources.** `reads_untrusted` and the `untrusted_source` node kind are implemented (1.3a, 2026-10-21); the write side of the channel — `mcp_server → writes_to → untrusted_source` — is implemented for the `mcp_tool_description` family (1.3a.1, 2026-10-21). Taint propagation is not. Chain groups and propagation remain ADR-0010 and backlog item 1.3. `flow_kind` and `data_flow_confirmed` prepared the ground.
2. **Chain groups.** Non-linear chains through untrusted sources are ADR-0010 and backlog item 1.3. `flow_kind` gives chain groups their material but does not build groups.
3. **Graph densification.** Call-graph edges and import edges (backlog item 1.5) are deferred until flow semantics are in place. Densification without `flow_kind` would worsen the false-positive rate.
4. **Framework-specific data-flow enrichment.** Each detector may upgrade `data_flow_confirmed` for its edges. Not implemented in this ADR; documented as an enrichment point.
5. **Full dataflow analysis.** Type-aware tracking, inter-procedural analysis, dictionary and f-string resolution. Out of scope (ADR-0001).
6. **Separate edge kinds for control and data.** `calls` and `data_flows_to` as distinct kinds. Rejected in this ADR; may be revisited if `find_chains` needs to filter by edge kind rather than attribute.
7. **Configuration file.** The number of scan parameters (`max_hops`, `max_candidates`, `data_edges_only`, `frameworks`) is growing. A dedicated config file is a separate ADR.
8. **SCIP integration.** ADR-0002 proposed SCIP as a precision layer. The TSA investigation (backlog item 1.1) confirmed TSA does not provide call edges or type information, so flow-kind determination is our own AST analysis. SCIP would not change this.
9. **Runtime monitoring splits `provides_tool`.** Today `provides_tool` is a single `control` edge, because static analysis cannot separate "the server exposes this tool" from "this tool was invoked". Phase 2 runtime monitoring can observe invocation, so the edge may later carry two facts: the structural declaration, and a runtime-confirmed `control` (or `data`) edge once a call is seen. Deferred until Phase 2 exists. Until then the single `control` edge is the deliberately conservative approximation — an exposed dangerous tool counts as reachable.

## Decision

1. Every stored edge carries `flow_kind`: `control` | `data` | `structural`.
2. `has_access_to` additionally carries `data_flow_confirmed`: `parameter_match` | `local_var_match` | `call_result_match` | `literal_only` | `no_args` | `unknown`.
3. `flow_kind = "data"` when `data_flow_confirmed` is one of `parameter_match`, `local_var_match`, `call_result_match`. Otherwise `flow_kind = "control"`.
4. `uses_model`, `uses_tool`, `delegates_to` carry `flow_kind = "control"` and `data_flow_confirmed = "unknown"`. Framework detectors may enrich them.
5. `provides_tool` carries `flow_kind = "control"` and `data_flow_confirmed = "unknown"` — the access path to a tool is the candidate attack path. `writes_to` (added by 1.3a.1, ADR-0010) carries the same pair: a server that declares a tool catalogue *produces* the source, and that is a declaration, not a traced dataflow. `guards` carries `flow_kind = "structural"`. Structural edges do not participate in `find_chains`.
6. `find_chains` gains a `data_edges_only: bool = False` parameter. The default is off; control-only chains remain in the graph and are available for chain groups and manual review.
7. The Phase 3 prompt receives `flow_kind` (and `data_flow_confirmed` where present) on every edge. No hard confidence rules are imposed; the LLM decides.
8. The database is recreated per scan; no migrations are required.
