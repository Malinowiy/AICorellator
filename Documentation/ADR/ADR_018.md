# ADR-0018: Layer 3 Semantic Validation

**Status:** Accepted
**Date:** 2026-10-27
**Context:** Phase A — Layer 3 (Analysis), post-ADR-0016
**Revised:** 2026-10-30 — §2 extended (evidence presence as the third `validated_kind` level; B.9). See "Revision note 2" below.

---

## Context

ADR-0006 introduced Layer 3: deterministic validation of a chain
returned by the LLM ensemble. It defined one check — **existence**:
every node and every edge in the reported chain must exist in the
graph. A chain that cited a missing edge was rejected as a
hallucination.

Measured on the four primary corpora and on a hand-built reversed
chain, three failures of the existence-only model became visible:

1. **Direction is not checked.** A chain `[A, B, C]` with edges
   `[e_XY, e_YZ]` validated even if `e_XY` went from `A` to `X`, not
   to `B`. The chain looked like a path; it was not one.
2. **Node order is not checked.** The first node need not be an
   entry point; the last need not be a sink. A chain of arbitrary
   nodes, all of which exist, validated.
3. **The untrusted anchor is not checked.** A chain that claims to
   pass through an `untrusted_source` validated even if the node was
   not a source, had no `source_type`, or had no reader.

The consequence was a **reputation** problem, not just a correctness
one: `validated: true` was printed in every report, and a reader was
entitled to assume it meant "the chain was checked". It meant
"exists", which is a weaker and different claim. A voter that
returned `exploitable: true, evidence: []` produced `validated:
true`.

Two further facts shaped the decision:

- **`find_chains` cannot emit a direction-broken candidate.**
  `_dfs_paths` records an edge id only for an edge leaving the node
  it is standing on. Direction checking therefore does not protect
  against the enumerator; it protects against chains arriving by any
  other path (hand-built, re-evaluated, a future enumerator). This is
  defense in depth, not a fix to enumeration.
- **Chains without an `untrusted_source` are the common case.** The
  anchor check must be vacuous for them; a chain `entry → agent →
  sink` has no anchor and must not fail.

---

## Considered Options

### Option A: Keep existence-only; rename `validated` to `exists`

The field says "exists", not "validated". No new checks.

**Rejected.** The rename is honest but does not close the direction,
order, or anchor gaps. A chain that "exists" but is not a path is
still a finding a reader will act on. The gap is real, not
terminological.

### Option B: One check — `is_chain_connected` — and nothing else

Direction only. No typed check, no anchor check.

**Rejected.** Direction alone leaves the node-order gap (a chain of
arbitrary nodes, all connected, passes) and the anchor gap (a chain
through a fake source passes). Direction is necessary but not
sufficient.

### Option C: Four checks, one `validated` boolean, and a
`validated_kind` label

Existence, connected, typed, anchor. `validated` is the conjunction;
`validated_kind` records the highest level the chain reached
(`"existence"` or `"semantic"`), so a chain can be traced to *why* it
was accepted or rejected.

**Accepted.**

---

## Decision

**Adopt Option C.**

### The four checks, in order

`validate_chain(nodes, edges) -> (ok, validated_kind, notes)` runs
them in order and accumulates one note per failure. Existence is
checked first and alone: a chain with a missing node or edge does not
have a "direction" to check.

1. **Existence** — every node in `nodes` exists in the `nodes` table;
   every edge in `edges` exists in the `edges` table. Fails →
   `validated = False`, `validated_kind = "existence"`, note
   `"missing node: <id>"` or `"missing edge: <id>"`.
2. **Connected** — `len(edges) == len(nodes) - 1`, and for every `i`,
   the edge `edges[i]` has `source_id == nodes[i]` and
   `target_id == nodes[i+1]`. Fails → note
   `"disconnected: edge <id> target is <id>, expected <id>"` (or
   `"edge count: N edges, M nodes"`).
3. **Typed** — the first node has `kind == "entry_point"`; the last
   node is a sink by either rule the codebase already uses:
   `kind == "sink"` **or** has a capability in
   `patterns.SINK_CAPABILITIES` (ADR-0009 / ADR-0014). Intermediate
   node kinds are **not** checked. Fails → note
   `"first node <id> is <kind>, not entry_point"` or
   `"last node <id> is <kind>, not a sink"`.
4. **Untrusted anchor** — only when the chain contains at least one
   `untrusted_source` node. For each such node: it has `kind ==
   "untrusted_source"`, an attribute `source_type` in
   `patterns.UNTRUSTED_SOURCE_RULES`, and at least one outgoing
   `has_access_to` edge to a node with `reads_untrusted`. Chains
   without an anchor pass vacuously. Fails → note
   `"anchor <id>: missing source_type"` or
   `"anchor <id>: no reader with reads_untrusted"`.

All four pass → `validated = True`, `validated_kind = "semantic"`,
empty `notes`.

### `validated_kind`

`"existence"` means "exists, but not semantically coherent" — the
chain failed at check 2, 3, or 4, or at check 1. It is the
pre-ADR-0018 meaning, kept so that chains stored before A.4 read as
`"existence"` (the DB is recreated per scan, ADR-0003; this is a
read-path default, not a migration).

`"semantic"` means "exists and coherent" — the chain passed all four
checks. On every A.4 row, `validated_kind == "semantic"` iff
`validated is True`.

The two-value enum is deliberately small. If later a "connected but
not typed" chain is worth distinguishing from "disconnected", the
field becomes richer. Do not pre-build that. Two values now.

### `validation_notes`

`list[str]`, one short, name-based sentence per failed check (same
rule as `FlowDecision.evidence` — never source text, never values).
Empty when all checks pass. Rendered in the report under the chain's
reasoning when the chain is rejected.

### `chain_groups`

Chain groups get `validated_kind` too. The group's own Layer 3 check
(evidence membership, hop resolution) is unchanged; the label just
says which level the group reached. `"semantic"` when the group's
check passes, `"existence"` otherwise.

### What is **not** in this ADR

- **Voter evidence presence affecting validation.** B.9 in the
  backlog. A.4 does not change it: a chain that is connected, typed,
  and anchor-valid still validates even if every voter returned
  `evidence: []`. That is a separate rule, on a separate axis.
- **`run_eval.py` printing `validated_kind`.** The report has the
  notes; the CLI is one line and stays as it is until someone needs
  it. Backlog Low.
- **A wider validation vocabulary.** Two values now.

## Schema

Two columns on `chains`, one on `chain_groups`:

```sql
-- chains
validated_kind    TEXT,
CHECK (validated_kind IS NULL OR validated_kind IN ('existence', 'semantic'))
validation_notes  JSON NOT NULL DEFAULT '[]',
CHECK (json_valid(validation_notes))

-- chain_groups
validated_kind    TEXT,
CHECK (validated_kind IS NULL OR validated_kind IN ('existence', 'semantic'))
```

`validated_kind IS NULL` on a row means "stored before A.4"; the read
path (`ChainsRepository.from_row`) maps `NULL` to `"existence"`. The
database is recreated per scan (ADR-0003); no migration.

---

## Consequences

### Positive

1. **`validated: true` means something.** Existence, direction, node
   order, and anchor are all checked. A reader who sees `validated:
   true` and `validated_kind: "semantic"` can rely on it.
2. **Rejections are explainable.** `validation_notes` says which
   check failed and why, in one short sentence. Reports show it under
   the reasoning.
3. **Direction is defense in depth.** `find_chains` cannot emit a
   direction-broken candidate; the check protects chains arriving by
   any other path (hand-built, re-evaluated, a future enumerator).
4. **The anchor check and the detector cannot drift.**
   `UNTRUSTED_SOURCE_TYPES` is derived from
   `patterns.UNTRUSTED_SOURCE_RULES`, so a new source family grows
   both in one place (B.3 will land `user_upload` this way).
5. **Backward-compatible read.** Pre-A.4 rows read as `"existence"`.

### Negative

1. **`validated` is now stricter.** Chains that passed existence-only
   and fail a semantic check are rejected. This is the intent, but it
   is a reputation change: what the tool meant by "validated"
   yesterday is not what it means today. Documented here, and in
   BACKLOG §"Resolved questions" item 3.
2. **Direction check does not protect `find_chains`.** It protects
   chains that arrive by other paths. The enumerator's own invariant
   (`_dfs_paths` records edges leaving the current node) is the
   protection there; A.4 does not duplicate it.
3. **Two-value `validated_kind` may need to grow.** Deferred.

### Neutral

1. **The existence check is unchanged.** `is_chain_valid` keeps its
   signature and returns `validate_chain(...)[0]`; callers that only
   need the boolean do not change.
2. **The report's rejection section gains the notes.** No other
   section changes.
3. **ADR-0006 is marked `Superseded in part`.** Its existence-only
   description remains true as history; ADR-0018 is the current
   state.

---

## Deferred

1. **Voter evidence presence affecting `validated` (B.9).** A chain
   with no voter evidence still validates if it is coherent. That is
   a separate rule, on a separate axis.
2. **`run_eval.py` printing `validated_kind`.** One line; the report
   has the notes.
3. **A richer `validated_kind`.** Two values now; extend when the
   data says so.
4. **`user_upload` in the anchor check.** Not implemented as a source
   family (ADR-0010 gap, BACKLOG B.3). The check reads
   `patterns.UNTRUSTED_SOURCE_RULES` and grows for free when B.3
   lands.
5. **`ADR-0006` rewrite.** Superseded in part, not rewritten — ADR
   is a historical document.

## Decision

1. Layer 3 runs four checks in order: existence, connected, typed,
   untrusted-anchor. `validate_chain(nodes, edges) -> (ok,
   validated_kind, notes)` returns all three; `is_chain_valid` stays
   as the boolean wrapper.
2. `validated = True` iff all four pass. `validated_kind` is
   `"semantic"` in that case and `"existence"` otherwise.
3. `validation_notes` records one short sentence per failed check;
   `[]` when all pass.
4. `chains` gains `validated_kind` and `validation_notes`;
   `chain_groups` gains `validated_kind`. The DB is recreated per
   scan; no migration. `NULL` reads as `"existence"`.
5. The typed check uses `patterns.SINK_CAPABILITIES` (ADR-0009 /
   ADR-0014). The anchor check uses
   `patterns.UNTRUSTED_SOURCE_RULES`. Both sets are single sources of
   truth; the validator does not duplicate them.
6. `is_untrusted_anchor_valid` is vacuously true when the chain has
   no `untrusted_source`.
7. Direction is defense in depth: `find_chains` cannot emit a
   direction-broken candidate; the check protects chains arriving by
   any other path.
8. ADR-0006 is marked `Superseded in part by ADR-0018 (Layer 3)`.
   Its text is not rewritten.

   ## Revision note 2 (2026-10-30)

§1 and §2 defined `Chain.validated` as existence + semantic coherence, with `validated_kind ∈ {"existence", "semantic"}`. B.9 adds a third level:

- **Evidence presence.** At least one voter cited at least one edge **from the chain** (not from the whole graph). The per-voter `evidence_valid` / `evidence_unknown` fields already exist (ADR-0006 Layer 3, `evaluator._voter_response_dict`); B.9 aggregates them to `Chain.validated`.

The new shape:

- `Chain.validated` is true when existence, semantic coherence, **and** evidence presence all pass.
- `Chain.validated_kind` gains `"evidence"` as the highest level:
  - `"existence"` — only existence passed (pre-ADR-0018 meaning kept for read-path compatibility, per A.4).
  - `"semantic"` — existence + semantic (A.4 meaning).
  - `"evidence"` — existence + semantic + evidence (**new**).
- `Chain.validation_notes` gains one entry when evidence fails: `"no voter cited an edge from the chain"`. The chain is stored with `validated: false`, `validated_kind: "semantic"` (the last level passed), and the note.
- A chain with no voters (all timed out) has no evidence; `validated: false`, `validated_kind: "semantic"`, note.
- A chain whose evidence cites edges **outside** the candidate chain (a hallucinated citation) fails evidence; the note names the count.

**What does not change:**

- The existence and semantic checks (A.4) are unchanged; they run first, and a failure there short-circuits (evidence is not reached).
- `Chain.validated_kind`'s read path is unchanged: a row with `NULL` reads as `"existence"` (pre-A.4), a row with `"semantic"` reads as `"semantic"` (pre-B.9). No migration; the DB is recreated per scan.
- The chain-groups path: `chain_groups.validated` is B.4b's check (edge membership + hop resolution), which already folds the voters' evidence into the group's `validated`; B.9 adds evidence for the linear chain path only.

**Why a revision, not a new ADR:** ADR-0018 §1 already names `"existence"` and `"semantic"`; B.9 adds a **third** level to the same concept. A new ADR would duplicate §1; a revision extends it. The precedent is ADR-0021's revisions.

**Risks:** chains stored before B.9 with `validated: true` become retroactively weaker under the new rules. The DB is recreated per scan (ADR-0003), so this is not a migration — it is a reputation change, recorded here and in the B.9 commit.
