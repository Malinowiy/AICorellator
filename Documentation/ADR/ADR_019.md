# ADR-0019: Guardrail emission and evaluation weighting

**Status:** Accepted
**Date:** 2026-10-29
**Supersedes in part:** ADR-0007
**Related:** ADR-0009 (capabilities), ADR-0010 (chain groups), ADR-0015 (`flow_kind`), ADR-0016 (control-only AST)

---

## Context

ADR-0007 registered the `guards` edge kind and declared its intent — a guardrail is a defensive control on a path — but it was honest that nothing emitted the edge: "`guards` is registered, `flow_kind = "structural"`, and nothing emits it." `guardrail` nodes exist (classified by `classification.py` from capabilities and, before ADR-0016, from class-name suffixes), but they are inert: they sit in the graph, `find_chains` does not traverse `structural` edges, and the LLM never learns that a guardrail exists anywhere near the path it is evaluating.

This is worse than having no guardrail nodes at all: the report's prompt asks the model "are there guardrails on the path?" while the payload contains nothing that would let the model answer. The model either ignores the question or, if a `guardrail` node happens to be adjacent in the graph, guesses at its role from its name. Neither is acceptable.

Two distinct questions were conflated in ADR-0007's deferred item:

1. **Emission.** What evidence establishes that a `guardrail` node protects a given component? This is a structural question — it is about which edges exist in the graph.
2. **Influence.** Given that a guardrail is on (or near) a path, what should the evaluation do with that fact? This is a policy question — it is about `find_chains` traversal and the prompt payload.

ADR-0019 answers both, in that order.

---

## Decision

### 1. Emission (B.4a)

`guards` edges are emitted **only when the source-level evidence establishes a protection relationship**. Three forms of evidence qualify, and only these:

- **Call site.** A component's body calls a function or method that is a `guardrail` node, resolved through the call graph (`ctx.entry_points.call_graph`, the same name-keyed call graph `entry_to_sink` and `delegation_edges` use). The edge is `guardrail → component`.
- **Decorator.** A component is decorated with `@guardrail(...)` (or an equivalent decorator whose target is a `guardrail` node — the same rule by which `@tool` marks a tool in `framework_detectors/langchain.py`). The edge is `guardrail → component`.
- **Not emitted, deliberately:**
  - **Co-location.** A guardrail and a component in the same file do **not** establish protection. It is not a defensive relationship; it is a file layout. Emitting `guards` on co-location would be a false claim about protection and, once emission feeds evaluation (below), a false claim that would **lower confidence on chains that no guardrail actually protects**.
  - **A `guardrail` class with no call site.** A guardrail that is wired in by dependency injection, a framework hook, or an import side effect is **not** emitted. This is a false negative, and it is accepted: a false negative leaves confidence where it was; a false positive moves it down for a reason the code does not support.
  - **`self.`-prefixed calls.** `self.pii_detector.check(x)` does not appear in the call graph (which records `ast.Name` calls only; `entry_points._collect_call_names`). Extending the call graph is **not** part of B.4; it is a separate item, and it is a precondition for a second pass over this ADR.

The direction is `guardrail → component`, not the reverse. ADR-0007 says "`guards` describes a defensive control" — this reads as "this guardrail describes what it protects", which is `guardrail → component`. The reverse reads as "this component is protected by", which is the same fact with the wrong subject: the guardrail is the actor, the component is the object.

The edge is `flow_kind = "structural"` (ADR-0015, decision 5), `observed_by = ["ast"]` (the `Edge` default, ADR-0016), `data_flow_confirmed = NULL`. No data-flow claim is made — a guardrail's presence is not a statement about whether any value reached it.

### 2. Influence (B.4b)

A guardrail on or near a path **does not exclude the path and does not mark the path as blocked**. It **lowers the confidence the model assigns to the path**, and the model does the lowering, from the payload.

`find_chains` does not change. `guards` is `structural`, `structural` edges are not traversable (ADR-0015, decision 5), so no chain is added, removed, or filtered by the existence of a `guards` edge. The evaluator does not change: it enumerates candidates, serializes them, and sends them to voters as before.

What changes is the **payload**. A candidate chain's payload gains a `guardrails` section: every `guardrail` node connected to any node of the chain by a `guards` edge, with the node's attributes (whatever the AST knows — the class or function name, and, once D.6 lands, `policy` and `enforcement_point`). The section is informational; the model decides what to do with it.

The prompt gains a rule: **a guardrail on the path is evidence of an attempt to block, not evidence of a block.** The model is told:

- To acknowledge the guardrail(s) in its reasoning.
- To lower confidence **proportionally**, not to zero — a guardrail whose filtering rules are not in the payload may be effective, partially effective, or ineffective; the model cannot tell.
- That excluding an attack requires **specific rules of specific properties** (a prompt-injection guardrail that only checks for known attack strings does not stop an indirect injection through a document), and those rules are not in the payload. The model's reasoning should say so.
- That the absence of a guardrail is not evidence of exploitability — it is the default state of every path, and it does not raise confidence.

This is a deliberate ceiling. The AST does not know what a guardrail's rules are, and ADR-0019 does not pretend it does. The model is told that the guardrail is there and that the rules are unknown; anything more would be a fabricated claim about behavior the analysis never observed.

### 3. Both sides of a chain group

A chain group (ADR-0010) is a write chain and a read chain meeting at an `untrusted_source`. A guardrail may sit on either side, or both, or neither. The payload carries the `guards` edges **per side**: which guardrails touch the write chain, which touch the read chain, and which touch the shared anchor. The model weighs each side separately — a guardrail on the write side does not weigh on the read side's sink, and vice versa. `find_chain_groups` is unchanged for the same reason `find_chains` is: `guards` is `structural`, and structural edges do not participate in enumeration.

### 4. What is explicitly not done

- **No `bypassed_by` derived edge.** BACKLOG B.4 listed a reverse edge as a sub-problem; it is not needed for weighting (the model is told about guardrails that exist, not about guardrails that were bypassed — the AST does not know which was which), and it would require source-level analysis that B.4 does not have.
- **No `policy` / `enforcement_point` derivation.** That is D.6. B.4a emits `guards` with the attributes the AST already carries. When D.6 lands, it enriches the payload; B.4 does not wait for it.
- **No change to `find_chains` signature, traversal, or edge kinds.** Guardrail influence is a payload concern, not an enumeration concern.
- **No change to the report's shape.** The `guardrails` section appears in the LLM payload; the Markdown report's chain sections are unchanged. A report consumer that wants to see which guardrails were on a chain reads the `guardrails` section in the payload's `chains.json` — the report is a view, and its guards visibility is a separate decision.

## Rationale

### Why weighting, and not exclusion or marking

**Exclusion** — "a chain with a guardrail on it is not a candidate" — conflates the presence of an attempt at defense with its success. A prompt-injection guardrail that only matches known attack strings is a guardrail; a chain through it is still exploitable. Excluding the chain at enumeration time would suppress exactly the findings that prove the guardrail insufficient. It would also break ADR-0015's structural edge rule in practice: a `guards` edge would become, in effect, a traversal decision, which is the opposite of what "structural" means.

**Marking** — "the chain is enumerable and carries a `blocked_by_guardrail: bool`" — is better than exclusion but is a false binary. The boolean says "blocked", which is a claim about success that the analysis cannot support. A report reader, an LLM, and a downstream tool all treat `blocked: true` as "not exploitable", which is exactly the claim a guardrail's mere presence does not establish.

**Weighting** — "the payload contains the guardrails, the model lowers confidence proportionally, the reasoning says why" — is the only form that is honest about what the analysis knows. The analysis knows the guardrail exists. It does not know the guardrail's rules, its coverage, or its enforcement point (D.6 is not landed). Weighting sends the model what is known and lets the model weigh it; it also lets the model **say** that the evidence is insufficient to clear the chain, which is what a reader needs to see.

### Why emission is source-level and not co-location

Co-location is the shape of a false positive that is **invisible in the graph** — the edge looks like any other, and once evaluation weighs it, the confidence drop is real. Source-level evidence (a call, a decorator) is the shape of a claim the code actually makes: "this code calls this guardrail" or "this code is decorated with this guardrail". Where the code makes the claim, the edge repeats it. Where it does not, the edge is silent.

The false negatives this accepts — `self.`-calls, dependency-injected guardrails, framework-hooked guardrails — are the same kind of false negative the rest of the AST layer accepts (ADR-0001, ADR-0009): name-based, call-site-based, no type resolution. They are consistent with the layer, not a new kind of miss.

### Why `guardrail → component` and not `component → guardrail`

The subject of the sentence is the guardrail. "This guardrail protects this component" is what `guards` claims, and the edge direction is the claim's direction. The reverse direction — `component → guardrail` — reads as "this component is guarded by", which is the same fact with the component as the grammatical subject. There is no semantic difference in what the pair asserts, but the direction is the direction of the **actor**: a guardrail is the thing that guards; the component is the thing guarded. This matches ADR-0007's framing ("a guardrail is a defensive control") and the `guards` reading in ADR-0015, decision 5 ("a guardrail 'guards' an action but is not something execution flows along").

### Why the model, and not a fixed weight

A fixed weight (e.g. "presence of a guardrail drops confidence by 0.2") would be a policy masquerading as a measurement. It assumes every guardrail is equally effective, which is false (a strict allowlist is not a regex), and it assumes the drop is additive, which is false (three guardrails on a path are not three times as safe). The model reads the payload, sees the guardrails, and weighs them against everything else it sees — the chain's flow kinds, its capabilities, its depth, its evidence. That is what the ensemble is for (ADR-0005). The fixed-weight alternative replaces a calibrated judgment with a constant.

### What "the rules are not in the payload" buys

The prompt's rule — "excluding an attack requires specific rules of specific properties, and those rules are not in the payload" — is not a hedge; it is a description of the analysis's actual knowledge. It tells the model:

1. Not to over-credit a guardrail. "There is a guardrail" is not "the guardrail works".
2. Not to clear the chain. The chain may be exploitable through a path the guardrail does not cover, and the payload does not show the guardrail's coverage.
3. To state the insufficiency in its reasoning. A reader who sees the chain's confidence with "a PII guardrail is present, but its filtering rules are not in the payload and the payload does not establish that the guardrail covers this input" can make their own call.

## Consequences

- **`guards` edges exist** on the graphs B.4a produces, from source-level evidence only. The edge is `structural` and carries `observed_by = ["ast"]`, `data_flow_confirmed = NULL` — no data-flow claim, no traversal effect.
- **`find_chains` and `find_chain_groups` are unchanged.** Structural edges do not participate in enumeration; the payload, not the traversal, is where guardrails enter evaluation.
- **The prompt gains a `guardrails` section and a rule about it.** The prompt version is bumped; chains evaluated before B.4 carry a version that says so. The payload shape is additive — existing fields are unchanged — so a chain stored under an older prompt version is not invalidated by B.4.
- **The report is unchanged in its chain sections.** Whether the report should surface guardrails in its Markdown is a separate decision; B.4 does not make it. The bundle's `chains.json` gains the section in the payload, which is where a programmatic consumer can see it.
- **A false negative is left in place.** Guardrails wired by DI, framework hook, or `self.`-call are not emitted. This is stated in the module docstring of the emitter and in this ADR, so it is a known limitation, not an oversight. The fix is a call-graph extension (not B.4) and D.6 (not B.4) — the first widens `self.`-calls, the second gives the payload a `policy` / `enforcement_point` attribute for the guardrails it does see.
- **No ADR-0007 edit beyond the `Superseded in part` marker.** ADR-0007's decision (register `guards`, `structural`, do not emit) is not reversed; it is fulfilled. ADR-0019 is the decision ADR-0007 deferred to.
- **No `bypassed_by` edge.** If a future analysis establishes that a specific guardrail was bypassed on a specific chain, a separate ADR adds the edge; B.4 does not speculate.
