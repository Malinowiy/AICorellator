# ADR-0019: Guardrail emission and evaluation weighting

**Status:** Accepted
**Date:** 2026-10-29
**Supersedes in part:** ADR-0007
**Revised:** 2026-10-31 (rev 1)
**Related:** ADR-0009 (capabilities), ADR-0010 (chain groups), ADR-0015 (`flow_kind`), ADR-0016 (control-only AST)

---

## Context

ADR-0016 removed the class-A name heuristics that used to produce `guardrail` nodes (a `*Guardrail*` class suffix, a `guardrails/` path segment). After ADR-0016, `classification.py` answers `sink` / `agent` / `llm_endpoint` / `tool` from capabilities and nothing else — no `guardrail` branch, no name table. The `guardrail` node kind is in the schema (`VALID_NODE_KINDS`), in `Node`/`Edge` models, and in the prompt payload's `guardrails` section (B.4b), but **nothing deterministic produces a `guardrail` node**. The gap is recorded as `B.4-gap`.

The question this ADR answers is twofold:

1. **How does a `guardrail` node reach the graph?** (the producer)
2. **How does a guardrail affect the evaluation of a chain that passes near it?** (the weighting)

The answer to (1) was split into `B.4-gap-1` (capability) and `B.4-gap-2..5` (per-SDK detectors). The answer to (2) is the payload section B.4b. This ADR records both, and — rev 1 — **what a `guards` edge's target may be**, which `B.4-gap-5` left open.

---

## Decision

### §1 — A `guardrail` node reaches the graph from one of three producers, and a `guards` edge from source-level evidence only

**Producers, in precedence order** (ADR-0024 §1):

1. **A framework detector** (`B.4-gap-2..5`): Guardrails AI `Guard(...)`, NeMo Guardrails `LLMRails(...)`, LangChain `BaseCallbackHandler` subclass, FastMCP `Middleware` subclass. The detector reads the SDK's own convention (ADR-0011) and emits a `guardrail` node with `observed_by = ["ast", "framework:<name>"]`.
2. **A capability** (`B.4-gap-1`, ADR-0024 §2): `validates_input` is credited on a function or method **called from** a component (`agent` / `tool` / entry point with `reads_untrusted`) and carrying **none of** the four classifying capabilities. `classification.py` yields `guardrail` from it; the node's `observed_by` is `["ast"]`.
3. **The LLM classifier** (D.2): a symbol the deterministic layers did not classify, classified `guardrail` by the model. `observed_by = ["ast", "static_llm:<model_id>"]`.

Precedence is **detector > capability > LLM**, resolved by `DetectorMergeStage` on `(name, source_file)`: a detector node replaces a capability node, and an LLM node is dropped where a deterministic node exists (`runner.py`'s "deterministic wins on conflict").

**A `guards` edge** (`guardrail → component`, structural — ADR-0015 decision 5) is emitted **only** when the source-level evidence establishes a protection relationship. Two forms of evidence are recognized:

- **Call site.** The component's body calls the guardrail by bare name, recorded in the name-keyed call graph (`entry_points.call_graph`, the same one `entry_to_sink` and `delegation_edges` read). Membership, not reachability: a guardrail one hop away in a chain is not evidence.
- **Decorator.** The component carries a decorator whose last dotted segment is the literal name `guardrail` — `@guardrail`, `@guardrail(...)`, `@mcp.guardrail(...)`.

**Three forms are deliberately *not* evidence**, and emit nothing:

- **Co-location.** A guardrail and a component in the same file are a file layout, not a defensive relationship. Emitting on co-location would be a false claim about protection — and, once B.4b weighs guardrails into confidence, a false claim that lowers confidence on chains no guardrail protects.
- **A `guardrail` node with no call site and no decorator.** One wired in by dependency injection, a framework hook or an import side effect is a false negative, and it is accepted: a false negative leaves confidence where it was; a false positive moves it down for a reason the code does not support.
- **`self.`-prefixed calls.** `self.pii.check(x)` is not in the call graph, which records `ast.Name` calls only (ADR-0016). Widening the call graph is a separate item and a precondition for a second pass over this section.

**What a `guards` edge's target may be — rev 1.** `COMPONENT_KINDS` `guardrail_edges.py` declares which node kinds a `guards` edge can point at. Before rev 1 it was `{"agent", "tool"}`. Rev 1 adds `"mcp_server"`, with **its own evidence rule** (below), because a FastMCP middleware — the `B.4-gap-5` producer — is registered on a *server*, not called from a component's body:

> A `guards` edge `guardrail → mcp_server` is emitted when the middleware is **registered** on the server: an `add_middleware(...)` call site on the server object (`mcp.add_middleware(AuditMiddleware())`) or a `@mcp.middleware(...)` decorator on the middleware factory. The detector reads the server's own module AST (`ctx.module_for`) and matches the guardrail node's name against the registration's argument. **Co-location is still not evidence** — a middleware class and a server in the same file, with no registration call, emits nothing.

This is **not** a widening of `COMPONENT_KINDS` "because co-location was already allowed" — co-location is exactly what rev 1 refuses. It is a widening because the SDK gives a *registration* call site, which is source-level evidence of the same strength as the call-site and decorator forms above: `add_middleware` is the place the developer declares "this middleware runs on this server", and the AST sees it.

**ADR-0007 is not contradicted.** Its table ("Guardrail protects an agent or a tool") names what a guardrail protects *in the graph's vocabulary*; a `mcp_server` is the container those tools live in, and a middleware that runs on the server protects every tool the server exposes. The edge `guardrail → mcp_server` says "this middleware runs on this server"; the model weighs it for the chains that pass through that server's tools (see §3 rev 1). The table is a description of what the edge is *about*, not a restriction on the edge's target kind.

### §2 — A guardrail affects the verdict through the payload, not through enumeration

The `guards` edge is **structural** (ADR-0015 decision 5): it is not traversed by `find_chains` or `find_chain_groups`. A guardrail on or near a chain is not a path step — it is a *signal* about the path, and it reaches the model as a section of the payload:

```json
{
  "guardrails": [
    {"id": "...", "kind": "guardrail", "name": "PIIDetector",
     "capabilities": [], "attributes": {...}}
  ]
}
```

The payload section is read from the graph by `evaluator._guardrails_for_chain` (linear chains) and `evaluator._guardrails_for_group` (chain groups, partitioned by side: write / read / anchor). It is not a filter on enumeration, and it is not a marking of the chain: the chain is the same chain, and the verdict is the model's.

The model is told (system prompt, `PROMPT_VERSION v1.6.0`):

> A guardrail's presence is evidence of an attempt to block, not evidence of a block: its rules are not in the payload, so lower confidence proportionally rather than clearing the chain. Excluding an attack requires specific rules of specific properties: a prompt-injection guardrail that only matches known attack strings does not stop an indirect injection through a document, and a PII filter does not stop a shell command. Name the class of rule the chain would need, and note that the payload does not show it. The absence of a guardrail is not evidence of exploitability: a path with no `guards` edges is not stronger than one with them, and it does not raise confidence.

### §3 — Payload visibility, and what a guardrail on a container means — rev 1

`_guardrails_for_chain(store, node_ids)` reads `guards` edges whose target is one of the chain's node ids. This is correct for a guardrail that protects an `agent` or a `tool`: the edge points at the component the chain passes through.

Rev 1 adds one rule. A chain may pass through a tool that has a `parent_server`; the middleware protecting that server is a `guards` edge `guardrail → mcp_server`. The chain's tool node is not that edge's target, so the current read misses it — the model does not see a guardrail the graph holds. Rev 1 closes that gap:

> When `_guardrails_for_chain` is asked about a tool node that carries a `parent_server` attribute, it also returns the guardrails whose `guards` edge points at the `mcp_server` node with that name. The middleware protects the server, the server contains the tool, the chain passes through the tool — the model should see the middleware, and weigh it exactly as §2 says: an attempt to block, with unknown rules, lowering confidence proportionally.

The rule is one level (a tool's server, not a server's server), and it is read from the same `guards` edge — the graph does not gain a second edge, and `COMPONENT_KINDS` does not grow a second kind for the read. The payload's `guardrails` section is a flat list for a linear chain and a per-side partition for a group; rev 1 changes neither shape, only which guardrails the read returns.

Partial-widening note, stated because it is the honest limit. A middleware on a server protects every tool the server exposes; the `guards` edge says the server is protected, not which tool a given request invokes, and not whether a given tool's body is the one the middleware filters. The edge is a probability, as the prompt says: its presence lowers confidence on a chain that passes through the server's tools, and it does not clear it. Where a middleware does protect a specific tool differently (a per-tool rule, a tool that bypasses the middleware), the graph cannot say so — and the model is told the rules are unknown. A false lowering is accepted, because the model weighs it; a false raising (the pre-rev-1 behaviour, where the middleware was invisible to a tool-level chain) is not, and rev 1 removes it.

## Consequences

**Positive**

- A `guardrail` node is in the graph, with provenance that distinguishes its three producers (`observed_by`).
- A `guards` edge is emitted only where the source says "this component is protected by this guardrail" — a call site, a decorator, or (rev 1) a middleware registration.
- The model sees the guardrails the graph holds, and weighs them as attempts to block (a confidence signal), not as blocks (a filter).
- Rev 1: a FastMCP middleware is visible to a tool-level chain that passes through its server — the gap `B.4-gap-5` pinned (X1a) is closed for the payload, without widening the traversal rules.

**Negative**

- A guardrail's rules are not in the payload, so the model cannot reason about what the guardrail filters. The prompt states this (an attempt to block, rules unknown) and asks the model to name the class of rule the chain would need.
- A guardrail wired in by dependency injection or a framework hook, with no call site and no registration, is a false negative. Accepted (§1).
- A `guards` edge `guardrail → mcp_server` protects every tool the server exposes. A chain through one such tool sees the middleware and is weighed down; a chain through a tool the middleware does not actually filter is weighed down too. The direction is "lower confidence" (ADR-0019 §2), and a false lowering is the accepted trade.
- Corpus regression for rev 1 is deferred: the four corpora (FinBot, NMB, dvmcp, mcploitable) are not on this machine. The behaviour is pinned by the detector's tests (`B.4-gap-5`: `test_fastmcp_middleware_detector.py`, X1a / X1a′) and by the `guardrail_edges` tests; a full corpus run is a post-return check.

**Neutral**

- `guards` remains structural: no data flows along it, and `find_chains` does not traverse it. Rev 1 does not change this.
- The `guardrail` node's `observed_by` distinguishes the three producers. A consumer that wants only deterministic guardrails reads `["ast", "framework:*"]`; a consumer that wants all of them reads every `guardrail` node.

## Revision note 1 (2026-10-31)

`B.4-gap-5-followup`. `B.4-gap-5` (FastMCP middleware detector) pinned a behaviour it did not choose: a middleware registered on a server was a node and no edge, because `COMPONENT_KINDS` in `guardrail_edges.py` was `{"agent", "tool"}` and the SDK's registration call (`mcp.add_middleware(...)`) is an `ast.Attribute` call that the name-keyed call graph (ADR-0016) does not record. The reviewer's question — "does `mcp_server` become a `guards` target?" — is what this revision answers.

**What changed:**

- §1 gains the `mcp_server` target and its evidence rule: an `add_middleware(...)` call site or a `@mcp.middleware(...)` decorator, read from the server's own module AST (`ctx.module_for`), with co-location still refused. `guardrail_edges.py::COMPONENT_KINDS` grows to `{"agent", "tool", "mcp_server"}` when the code lands; the ADR is the decision, the code is the follow-up.
- §3 gains the payload rule: `_guardrails_for_chain` reads a `guards` edge on a tool's `parent_server` in addition to its own target. The graph gains no edge, the payload gains no section, the model sees the middleware the graph already holds.
- §1 gains the ADR-0007 reconciliation: its table names what a guardrail protects in the graph's vocabulary; a `mcp_server` is the container those tools live in, and a middleware that runs on the server protects every tool it exposes. The edge is `guardrail → mcp_server`; the model weighs it for the chains that pass through that server's tools (§3).
- The prompt (v1.6.0, B.4b) is unchanged: the §2 rule already says "a guardrail's presence is evidence of an attempt to block, not evidence of a block", and a middleware on a server is exactly that.

**What did not change, and why:**

- **Co-location is still not evidence.** A middleware class in the same file as a server, with no registration call, emits nothing.
- **`self.`-calls are still not evidence.** `self.middleware.check(x)` is not in the call graph.
- **`@guardrail` decorator semantics are unchanged.**
- **The `guards` edge stays structural.** `find_chains` does not traverse it; the guardrail reaches the model through the payload, not through the path.
- **ADR-0007's table is not rewritten.** It is read as a description of the edge's subject, not as a restriction on its target kind; a note is added to ADR-0007 pointing here.
- **Corpus regression is deferred, not skipped.** The four corpora are not on this machine; the decision is written now so it does not drift, and the code that implements it is briefed when the corpora return (or with an explicit "corpus regression deferred" note on the code commit).
- **`B.4-gap-5`'s X1a** (node-and-no-edge) becomes X1a's old negative — a middleware with no registration call still has no edge — and X1a′ stays a positive; the new positive is a registered middleware, `guards` edge `guardrail → mcp_server`, and a tool-level chain through that server seeing the middleware in the payload.
