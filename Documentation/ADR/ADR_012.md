# ADR-0012: Chain Group Prioritization

**Status:** Accepted
**Date:** 2026-10-12
**Last reviewed:** 2026-10-22
**Context:** ADR-0010 (multi-chain groups) — controlling combinatorial explosion

---

## Context

ADR-0010 introduces **chain groups**: sets of chains that meet through an `untrusted_source`. A group is dangerous when one chain **writes** to the source and another **reads** from it, reaching a sink.

The naive algorithm enumerates all combinations:

```
for each untrusted_source:
    write_chains = chains that write to it
    read_chains = chains that read from it
    for w in write_chains:
        for r in read_chains:
            evaluate(w + r)
```

For pairs, this is O(n²). For triples — O(n³). For groups of size k — O(n^k). Real multi-step attacks may require 3–4 chains, which approaches O(n!) in the worst case. At n=100, even O(n³) is 10⁶ combinations; each is an LLM call costing seconds.

This does not scale. The design must bound cost without missing high-value combinations.

---

## Considered Options

### Option A: Full enumeration, LLM-only evaluation

Evaluate every combination with the full LLM ensemble.

**Rejected.** Cost explodes. 10⁶ combinations × 3 voters × 2 minutes = years.

### Option B: Random sampling

Sample N combinations randomly.

**Rejected.** High-value combinations may be missed. No coverage guarantee.

### Option C: Fuzzing-style prioritization (deterministic)

Score each combination cheaply (no LLM), then send the top-N to the LLM ensemble.

**Accepted.**

### Option D: Groups around untrusted sources, not all combinations

Enumerate only groups that share a single untrusted source. This is the *structure* of indirect prompt injection: one channel, two sides (write and read).

**Accepted.** Combined with Option C.

### Option E: Small-model pre-scoring

Use a small LLM to score combinations, then send the top-N to the full ensemble.

**Deferred.** Optional. Not required for MVP.

---

## Decision

**Adopt a fuzzing-style layered prioritization with bounded group size:**

1. **Enumerate groups around untrusted sources** — not all combinations. A group is defined by one untrusted source, one or more writing chains, and one or more reading chains.
2. **Bound group size** — `max_chain_group_size` (default 2). Triples and larger are opt-in via config.
3. **Cheap score** each group — deterministic heuristics.
4. **Rank** groups by score.
5. **Evaluate top-N** with the full LLM ensemble.
6. **Expand** to larger groups only if explicitly enabled.

---

## Structure of a Chain Group

A chain group is defined by:

- **One `untrusted_source`** (ADR-0010).
- **A set of writing chains** — paths that terminate at the source.
- **A set of reading chains** — paths that originate from the source and reach a sink.

**Minimum viable group:** one write chain + one read chain. This is the canonical indirect prompt injection shape.

**Larger groups:** one write + two reads, two writes + one read, etc. Each additional chain must still meet at the same untrusted source. Groups are **connected by construction** — they cannot be arbitrary combinations.

**Why this bounds complexity:**

- Number of untrusted sources: small (typically < 20).
- Write chains per source: bounded by `max_hops` and `max_candidates`.
- Read chains per source: same.
- Pairs per source: O(w × r) — bounded by graph structure.
- Triples per source: O(w² × r) or O(w × r²) — larger but still bounded, and **off by default**.

The factorial blow-up of "any 4 chains from any source" does not occur, because chains must share the untrusted source.

## Cheap Scoring

Score is computed from capabilities (ADR-0009) and structure. **No LLM.**

### Scoring components

| Signal | Weight | Rationale |
|---|---|---|
| Reading chain passes through a lethal trifecta node | +5 | ADR-0009 — direct signal |
| Reading chain reaches `executes_shell` / `executes_code` sink | +4 | High-impact action |
| Reading chain reaches `writes_filesystem` / `http_egress` sink | +3 | Data manipulation / exfil |
| Reading chain reaches `writes_db` sink | +3 | Persistent data mutation (see revision below) |
| Writing chain reaches the untrusted source from an authenticated entry point | +2 | Plausible attacker path |
| Untrusted source is user-writable (`user_upload`, `rag_corpus`) | +2 | Attacker can place data |
| Untrusted source is user-readable only (`mcp_tool_description`) | +1 | Poisoning requires more control |
| Short total chain length (fewer hops) | +1 | Simpler to exploit |
| Any node has `confidence < 0.7` (stale) | −2 | Uncertain graph data |
| Writing chain and reading chain share an entry point | +2 | Same attacker can trigger both |

**Score range:** approximately 0–20. Higher = more promising.

Scoring is deterministic and takes milliseconds per group.

### Revision 2026-10-22 — `writes_db` added

The original table weighted `executes_*`, `writes_filesystem`, and `http_egress` as sink impacts, but not `writes_db`. On the FinBot corpus, the read-side sinks that untrusted input can reach are `writes_db` methods (`create_email`, `delete_file`, `create_transfer`, `update_status`, ...) — 109 nodes carry the capability. Without a `writes_db` weight, every FinBot group scored exactly 1 (`user_readable_source`), and none exceeded `min_score_to_evaluate = 5`. Zero groups were selected, even though the corpus has real indirect-prompt-injection candidates.

The omission is the same class of gap as the one that produced the 0 `data` edges before ADR-0015: the scoring vocabulary did not intersect the corpus's actual impact vocabulary. `writes_db` is a persistent side-effect — the same class as `writes_filesystem` — and is weighted identically (+3). `reads_db` remains unweighted: reading is not the impact; the write is.

### Threshold revision — `min_score_to_evaluate`

With `writes_db` weighted, the minimum useful score changes. A group with a `user_readable_source` (+1) and a `writes_db` read-side sink (+3) scores 4. The original threshold of 5 would still select zero. The threshold is revised to **3**: a group must have at least one weighted impact signal above the baseline `user_readable_source` to be worth the LLM call. A group with `user_writable_source` (+2) alone does not pass; it needs a sink. A group with `writes_db` (+3) alone passes. This matches the intent: a source alone is not dangerous; a source plus a write is.

### Skipped signals (deliberate)

**Authenticated entry point** and **shared entry point** are pinned at 0 and not added to the score:

- **Authenticated entry point.** The graph does not model authentication. Applying +2 to every entry point is a constant, not a signal. A pattern-based detection (`Depends(get_current_user)`, `require_auth` decorator) has no corpus to validate against. Pinned at 0 until authentication is modelled (deferred).
- **Shared entry point.** A write chain starts at an entry point; a read chain starts at the source. They cannot share a first node by construction. The ADR's wording ("writing chain and reading chain share an entry point") is aspirational: the shape it describes is not producible by this enumerator. Reinterpreting it ("the entry point also starts some other chain that reads the source") would invent a signal the ADR does not state. Pinned at 0.

The `score_components` JSON carries both keys with a `reason` explaining the skip, so the analyst sees the decision, not a silent zero.

## Group Size Constraints

| Parameter | Default | Meaning |
|---|---|---|
| `max_chain_group_size` | 2 | Pairs only. Triples and beyond are opt-in. |
| `enable_triples` | false | Enable groups of size 3 |
| `enable_quadruples` | false | Enable groups of size 4 |

**Default behavior:** only pairs (one write chain + one read chain).

**Why pairs by default:**

1. **Indirect prompt injection** — the canonical AI attack — is a pair: plant the payload, trigger the read.
2. **Cost is bounded** — O(w × r) per source, not O(n!).
3. **Signal-to-noise is high** — pairs cover the common case.

**Enabling triples/quadruples** is a deliberate opt-in for research or high-security environments. Users accept the cost.

## Ranking and Selection

Groups are sorted by score, descending. The top-N are selected:

| Parameter | Default | Meaning |
|---|---|---|
| `max_groups_scored` | 10000 | Hard cap on groups enumerated |
| `max_groups_evaluated` | 100 | Hard cap on groups sent to LLM |
| `min_score_to_evaluate` | 3 | Skip groups below this score |
| `analysis_budget_seconds` | 3600 | Wall-clock budget for LLM phase |

Selection algorithm:

```
groups = enumerate_groups_around_sources()   # bounded by structure
scored = [(score(g), g) for g in groups]
scored.sort(reverse=True)
selected = [
    g for s, g in scored
    if s >= min_score_to_evaluate
][:max_groups_evaluated]
```

**Result:** the top-N most promising groups, regardless of total enumeration size.

**Tiebreaker.** `group_id` (content-derived sha256 prefix). Scoring ties are common; input order is a property of the enumeration, not of the group, so a re-run with a different `max_groups_scored` must select the same groups.

**Enumeration cap and scoring cap.** The caller should pass `max_groups ≥ max_groups_scored`, otherwise the enumerator's cap — not the ranker — decides what can be selected. The enumerator truncates in id order, before scoring sees the groups. This is a wiring concern for 1.3e; flagged in the 1.3c report.

## Data Model

Each chain group in `chain_groups` carries a score and its breakdown:

```sql
-- In chain_groups (from ADR-0010):
score REAL NOT NULL DEFAULT 0.0,
score_components JSON NOT NULL DEFAULT '{}',
priority TEXT,  -- low | medium | high
```

`score_components` stores the breakdown — which capabilities and signals contributed. Used for debugging, for report rendering, and for the analyst to see why a group scored what it did. Keys are stable and one-per-signal (9 keys); a `reasons` object carries a short name-based explanation per key.

**`priority` buckets:** `high` if score ≥ 15, `medium` if score ≥ 10, `low` otherwise. Cutoffs are configurable.

## Consequences

### Positive

1. **Cost is bounded by config**, not by combinatorics. Even with thousands of pairs, LLM evaluation stays bounded.
2. **High-value groups surface first.** Lethal trifecta and dangerous sinks rank highest.
3. **Deterministic scoring** — reproducible, testable, no LLM cost.
4. **Groups are connected by construction.** No factorial blow-up.
5. **Pairs by default.** Covers indirect prompt injection, the main AI multi-chain attack.
6. **Small-model pre-scoring is optional** — off by default.
7. **`writes_db` is weighted** (2026-10-22 revision). Persistent data mutation is a real impact, parallel to `writes_filesystem`.

### Negative

1. **Misprioritization is possible.** A dangerous group with a low score may not reach the top-N. Accepted trade-off.
2. **Score weights are heuristic.** May need tuning per target. The `writes_db` revision is the first such tuning; more may follow.
3. **`min_score_to_evaluate` threshold** is arbitrary without a reference corpus. Revised from 5 to 3 in the same pass; still heuristic.
4. **Triples and quadruples off by default** — may miss complex multi-step attacks. Accepted trade-off: cost control over completeness.
5. **Two signals are skipped** (authenticated entry, shared entry) — pinned at 0 with a reason. Real signals once authentication is modelled and the enumerator produces a shape they describe.

### Neutral

1. **Deterministic scoring is testable** without an LLM.
2. **Small-model pre-scoring is optional** — off by default.
3. **Group structure is a constraint**, not a heuristic.

---

## Not in Scope

- Automatic weight learning from feedback.
- Runtime cost prediction (before running the LLM).
- Distributed evaluation across multiple hosts (Phase 3+).
- Groups larger than 4 (not currently envisioned).

---

## Deferred

1. **Small-model pre-scoring.** Optional, off by default.
2. **Adaptive group size.** Increasing size when score is high.
3. **Cross-source groups.** Groups spanning multiple untrusted sources. Not currently modeled.
4. **Authentication model.** Required for the `authenticated_entry` signal (currently pinned at 0).
5. **Shared-entry signal.** Requires an enumerator shape that produces it; the current `find_chain_groups` does not.
6. **Triples and quadruples.** `max_chain_group_size > 2` is opt-in; the scoring and selection code paths for larger groups are not implemented (1.3c.1).

## Decision

**Chain groups are enumerated around untrusted sources, not as arbitrary combinations. Default group size is 2 (pairs), which covers indirect prompt injection. Triples and quadruples are opt-in. Cost is bounded by config, not by combinatorics. Deterministic scoring selects the top-N for LLM evaluation.**

**Revision 2026-10-22:** `writes_db` added to the scoring table at +3, parallel to `writes_filesystem`. `min_score_to_evaluate` revised from 5 to 3. Authenticated entry and shared entry signals pinned at 0 with a reason. The revision is grounded in the 1.3c report: on FinBot all 2920 groups scored 1 without `writes_db`, and none exceeded the original threshold.
