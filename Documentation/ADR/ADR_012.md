# ADR-0012: Chain Group Prioritization

**Status:** Proposed
**Date:** 2026-10-12
**Context:** ADR-0010 (multi-chain groups) — controlling combinatorial explosion

---

## Context

ADR-0010 introduces **chain groups**: sets of chains that meet through
an `untrusted_source`. A group is dangerous when one chain **writes**
to the source and another **reads** from it, reaching a sink.

The naive algorithm is:

```
for each untrusted_source:
    write_chains = chains that write to it
    read_chains = chains that read from it
    for w in write_chains:
        for r in read_chains:
            evaluate(w + r)
```

This is O(n²) at minimum, and each evaluation is an LLM call
(seconds to minutes per chain). On FinBot alone:

- 180 candidate chains.
- 5 untrusted sources (hypothetically).
- 4 read/write chains per source → 4 × 4 = 16 pairs per source.
- 5 × 16 = **80 pairs**.
- 80 pairs × 3-voter full ensemble × 2 minutes = **8 hours**.

Scaling to triples and quadruples makes this worse. LLM evaluation
cost must not grow linearly with combinatorial combinations.

---

## Considered Options

### Option A: Full enumeration, LLM-only evaluation

Evaluate every pair with the full LLM ensemble.

**Rejected.** Cost explodes. 8 hours for the simplest case. No
prioritization.

### Option B: Random sampling

Sample N pairs randomly, evaluate them.

**Rejected.** High-value pairs may be missed. No guarantee of
coverage on the dangerous combinations.

### Option C: Deterministic scoring, then LLM

Score each pair cheaply (deterministic, no LLM), then send the
top-N to the LLM ensemble.

**Accepted.**

### Option D: Small model pre-scoring

Use a small LLM to score pairs, then send the top-N to the full
ensemble.

**Accepted as a complement to C, not a replacement.**

---

## Decision

**Adopt a fuzzing-style layered prioritization:**

1. **Enumerate** all chain groups (write × read) — deterministic.
2. **Cheap score** each group — deterministic heuristics.
3. **Rank** groups by score.
4. **Evaluate top-N** with the full LLM ensemble.
5. **Expand** to triples/quadruples only if budget allows.

---

## Cheap Scoring

Score is computed from capabilities (ADR-0009) and structure.
**No LLM.**

### Scoring components

| Signal | Weight | Rationale |
|---|---|---|
| Reading chain passes through a lethal trifecta node | +5 | ADR-0009 — direct signal |
| Reading chain reaches `executes_shell` / `executes_code` sink | +4 | High-impact action |
| Reading chain reaches `writes_filesystem` / `http_egress` sink | +3 | Data manipulation / exfil |
| Writing chain reaches the untrusted source from an authenticated entry point | +2 | Plausible attacker path |
| Untrusted source is user-writable (`user_upload`, `rag_corpus`) | +2 | Attacker can place data |
| Untrusted source is user-readable only (`mcp_tool_description`) | +1 | Poisoning requires more control |
| Short total chain length (fewer hops) | +1 | Simpler to exploit |
| Any node has `confidence < 0.7` (stale) | −2 | Uncertain graph data |
| Writing chain and reading chain share an entry point | +2 | Same attacker can trigger both |

**Score range:** approximately 0–20. Higher = more promising.

### Deterministic scoring

All scoring is deterministic. Same graph → same scores. No LLM.
Takes milliseconds per group.

---

## Ranking and Selection

Groups are sorted by score, descending. The top-N are selected
based on configuration:

| Parameter | Default | Meaning |
|---|---|---|
| `max_pairs_scored` | 10000 | Hard cap on groups enumerated |
| `max_pairs_evaluated` | 100 | Hard cap on groups sent to LLM |
| `min_score_to_evaluate` | 5 | Skip groups below this score |
| `analysis_budget_seconds` | 3600 | Wall-clock budget for LLM phase |

Selection algorithm:

```
groups = enumerate_all_pairs()           # capped at max_pairs_scored
scored = [(score(g), g) for g in groups]
scored.sort(reverse=True)
selected = [
    g for s, g in scored
    if s >= min_score_to_evaluate
][:max_pairs_evaluated]
```

**Result:** the top-N most promising groups, regardless of total
enumeration size.

---

## Optional Small-Model Pre-Scoring

For large graphs (>10000 pairs), a small LLM (e.g. Qwen3-4B) can
pre-score pairs before the deterministic scoring:

1. Small model scores each pair 0–10 with a one-line reason.
2. Deterministic scoring adjusts the small-model score.
3. Top-N go to the full ensemble.

**Status:** optional, not required for MVP. May be added in
Phase 2+ if deterministic scoring proves insufficient.

**Cost:** small model at ~50 tok/s → 10 seconds per 100 pairs.
Acceptable.

**Risk:** small model may be wrong. Score is used only for
**ranking**, not for final verdict. Misranked pairs are not lost —
they simply score lower and may not reach the top-N.

---

## Expansion to Triples and Beyond

After pairs are evaluated, if budget remains:

1. **Triples:** one write chain + two read chains meeting at the
   same untrusted source. Score = sum of pair scores + bonus for
   shared entry point.
2. **Quadruples and beyond:** rarely useful. Skip unless requested.

**Default:** triples are disabled in MVP. Enabled via config:

```yaml
chain_groups:
  enable_triples: false
  enable_quadruples: false
```

---

## Progress and Control

Progress reporting, user stop, and directional scan control are
**backlog items**. They are not in the first or second
implementation queue.

**MVP:** all control is via config:

```yaml
chain_groups:
  max_pairs_scored: 10000
  max_pairs_evaluated: 100
  min_score_to_evaluate: 5
  analysis_budget_seconds: 3600
  enable_triples: false
```

**Later (backlog):**
- CLI progress with ETA.
- Ctrl+C-safe interruption.
- Interactive selection of untrusted sources to prioritize.

---

## Data Model

Each chain group in `chain_groups` carries a score:

```sql
-- In chain_groups (from ADR-0010):
score REAL NOT NULL DEFAULT 0.0,
score_components JSON NOT NULL DEFAULT '{}',
```

`score_components` stores the breakdown — which capabilities and
signals contributed. Used for debugging and for report rendering.

---

## Consequences

### Positive

1. **Cost is bounded by config**, not by combinatorics. Even with
   thousands of pairs, LLM evaluation stays bounded.
2. **High-value groups surface first.** Lethal trifecta and dangerous
   sinks rank highest.
3. **Deterministic scoring** — reproducible, testable, no LLM cost.
4. **Optional small-model layer** — can be added later without
   changing the pipeline.
5. **Same mechanism as fuzzing** — cheap filter, then focused deep
   analysis.

### Negative

1. **Misprioritization is possible.** A dangerous group with a low
   score may not reach the top-N. Accepted trade-off.
2. **Score weights are heuristic.** May need tuning per target.
3. **`min_score_to_evaluate` threshold** is arbitrary without a
   reference corpus.

### Neutral

1. **Deterministic scoring is testable** without an LLM.
2. **Small-model pre-scoring is optional** — off by default.
3. **Triples and quadruples are off** by default.

---

## Not in Scope

- Automatic weight learning from feedback.
- Runtime cost prediction (before running the LLM).
- Distributed evaluation across multiple hosts (Phase 3+).

---

## Decision

**Chain groups are prioritized by deterministic scoring on
capabilities and structure. Top-N groups go to the LLM ensemble.
Cost is bounded by config, not combinatorics. Small-model
pre-scoring and triple/quadruple expansion are optional and off
by default. UI/CLI control is backlog.**
