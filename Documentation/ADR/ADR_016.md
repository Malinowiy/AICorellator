# ADR-0016: Control-Only AST Layer and `observed_by` as a First-Class Attribute

**Status:** Proposed
**Date:** 2026-10-25
**Context:** Layer 1a (AST) and Layer 2 (runtime), post-v0.1

---

## Context

ADR-0015 introduced `flow_kind` (`control` | `data` | `structural`)
and `data_flow_confirmed` (six values) on every edge, with the promise
that the AST layer would distinguish "X calls Y" from "data from X
reaches Y". That promise was not kept.

Measured on the four primary corpora (FinBot, NMB, dvmcp, mcploitable):

- `data_flow_confirmed = "unknown"` on **100%** of edges.
- `data_edges_only = 0` on **every** corpus.
- `FlowKindStage` derives `flow_kind = "control"` from `"unknown"`,
  so every edge is control. The `data` value never appears on an
  AST-only scan.

This is not a bug in `flow/arguments.py`. The argument classifier
does exactly what it documents: name-based matching, one level deep,
no value tracking (ADR-0001). `config.get("path")`, `f"{base}/{name}"`,
`obj.attr` are all `unknown` by design. Real code is full of these
shapes. The classifier is correct; the promise was wrong.

Two further facts force the decision:

1. **The AST cannot answer the question.** Separating control flow
   from data flow requires type resolution, interprocedural analysis,
   and symbolic execution — years of work that mature SAST tools have
   already done, and that AICorellator explicitly does not attempt
   (ADR-0001). The AST layer will never be able to confirm data flow
   with acceptable precision, and pretending otherwise produces
   `unknown` on every edge, which is worse than `NULL` because it
   looks like a signal.

2. **Runtime and static analysis produce different graphs.** Runtime
   taint tracking observes *executed* code: function calls, tainted
   values, sinks reached. The AST observes *all* code: functions
   defined, calls written, sinks declared. They do not map 1:1. The
   mapping key is `(file_path, line_start, symbol_name)` — TSA
   provides it (`TSASymbol.line_start`), and Python frames provide it
   (`co_filename`, `co_firstlineno`, `co_name`). Splicing the two is
   a separate engineering task, and the graph must be able to
   represent it.

ADR-0015's `data_flow_confirmed` conflates *what* kind of flow an
edge is with *who* established it. The two are orthogonal. An edge can
be control by AST and data by runtime (observed invocation). An edge
can be data by AST heuristic and *not* observed by runtime (the test
did not cover it). A single six-valued field cannot express this.

---

## Considered Options

### Option A: Keep ADR-0015 as is; treat `unknown` as the honest answer

Do nothing. `data_flow_confirmed = "unknown"` on AST edges, `data` only
when a runtime layer populates it. `data_edges_only` returns `[]` on
AST-only scans.

**Rejected.** `unknown` is a value of the *answer set* — it means "the
analyzer looked and could not decide". On AST edges, the analyzer did
not look and cannot look. The honest value is `NULL`, which means
"this layer does not answer this question". The distinction matters
for the prompt (the LLM should not weigh "analyzer tried and failed"
the same as "analyzer never asked"), for reports, and for the runtime
stitcher (which needs to know which edges it is confirming).

### Option B: Replace `data_flow_confirmed` with a single expanded enum

Extend the set: `NULL` | `observed_match` | `runtime_only` |
`ast_control`. One field, more values.

**Rejected.** The field would then answer two questions at once ("how
was flow established" and "who established it"), and the answers are
independent. An edge can be `parameter_match` + `["ast", "runtime"]`
(both agree) or `parameter_match` + `["ast"]` (AST guesses, runtime
never saw it). One field cannot carry both facts, and the prompt
would have to parse the value to recover the source. It also does
not scale: a third runtime run, a symbolic executor, a manual review
— each would need a new enum value.

### Option C: Two orthogonal attributes

Keep `flow_kind` and `data_flow_confirmed` as they are, and add
`observed_by` — a JSON array of strings identifying who confirmed the
node or edge. `observed_by = ["ast"]` on every Layer 1a node and edge.
Layer 2 adds `"runtime"`. Multiple runs add `"runtime:test_foo"`,
`"runtime:test_bar"`. A third-party tool can add `"symbolic:angr"` or
`"manual:reviewer-a"`.

**Accepted.**

---

## Decision

**Adopt Option C.**

### `observed_by` on nodes and edges

Every node and every edge carries `observed_by`, a JSON array of
strings. Default `["ast"]`. Required — an empty array is a
construction bug.

Values are open-ended strings. The system defines these prefixes:

| Value | Meaning |
|---|---|
| `"ast"` | The structural layer observed this. Every Layer 1a node and edge. |
| `"runtime"` | A runtime run observed this. Added by Layer 2. |
| `"runtime:<run_id>"` | A specific runtime run. Used when multiple test runs are stitched. |
| `"static_llm:<model_id>"` | The LLM classifier added this. Layer 1b. |

Adding a new prefix is not a schema change — `observed_by` is a JSON
array, and the CHECK constraint (below) only requires valid JSON.

### `flow_kind` on AST edges is always `control`

`FlowKindStage` sets `flow_kind = "control"` on every AST edge and
**does not read** `data_flow_confirmed`. The derivation
`flow_kind_for(decision)` remains in `flow/decision.py` as the single
mapping, but on Layer 1a it is applied only to the `"control"` case.
`flow_kind = "data"` appears only when a runtime observation adds
`"runtime"` to `observed_by` and the edge is confirmed as a data path.

**Consequence:** `find_chains(data_edges_only=True)` filters on
`"runtime" in observed_by`, not on `flow_kind = "data"`. On an
AST-only scan it returns `[]`. This is correct and documented.

### `data_flow_confirmed` is `NULL` on AST edges

The `flow/` analyzers still run — they are the mechanism by which
Layer 2 will confirm data flow when it exists. But their result is not
stored on AST edges. `data_flow_confirmed` is `NULL` on every AST edge
and is populated only by Layer 2, which runs `flow/` against a
`(tool_func, sink_call)` pair **that runtime observed**, not one the
AST guessed.

**Consequence:** the `FlowDecision` type and `flow/` module remain,
but `FlowKindStage` no longer writes their output. The output is
consumed by Layer 2's stitcher instead.

### Classification layers

The classification pipeline becomes five layers, in order:

| # | Layer | Determinism | When |
|---|---|---|---|
| 0 | TSA symbols | deterministic | always |
| 1 | Framework detectors | deterministic | always (per `scan.yaml`) |
| 2 | Capability extraction | deterministic | always |
| 3 | User detectors | deterministic (user's responsibility) | per `scan.yaml` |
| 4 | LLM classifier | non-deterministic without cache | per `scan.yaml` |

User detectors are `FrameworkDetector` subclasses loaded from paths
(`framework_detectors/loader.py`). They are **not a separate concept**
from built-in detectors — the same interface, the same registry, the
same runner. The only difference is that a built-in detector is
imported statically and a user detector is imported from a path.

The LLM classifier runs **after** the deterministic layers and is
invoked **only** for symbols the deterministic layers did not classify
(`mode: auto`). `mode: required` invokes it for every symbol;
`mode: off` never invokes it. The mode is in `scan.yaml`, not a CLI
flag.

### Scan policy is `scan.yaml`, not flags

CLI flags are minimized to `--target`, `--config`, `--clean`.
Everything else — which detectors run, whether the LLM classifier
runs, whether runtime runs, what to do with unclassified symbols,
how many log archives to keep — is in `config/scan.yaml`. The file
is created from a template on first run with a warning. It is a
user input, not state; `--clean` does not touch it.

### Removal of class-A name heuristics

`SINK_METHOD_NAMES`, `SINK_CATEGORY_HINTS`, `RUNNER_TO_AGENT`,
`EXTRA_AGENT_CLASSES`, `PROVIDER_HINTS`, `TOOL_METHOD_PREFIXES`,
`SKIP_METHOD_NAMES` are removed from `patterns.py`. `classification.py`
classifies by capabilities and framework provenance only. LLM
classification is the replacement for body-aware decisions these
heuristics approximated; it is opt-in because it is expensive and
because a user detector can cover the same case deterministically.

## Schema

Two new columns. The database is recreated per scan (ADR-0003); no
migration is required.

```sql
-- nodes
observed_by JSON NOT NULL DEFAULT '["ast"]',
CHECK (json_valid(observed_by))

-- edges
observed_by JSON NOT NULL DEFAULT '["ast"]',
CHECK (json_valid(observed_by))
```

`Edge.upsert` and `Node.upsert` merge `observed_by` as a set union,
matching the existing merge semantics for `capabilities`. A later
write with `["runtime"]` on an edge that has `["ast"]` produces
`["ast", "runtime"]`. This is what makes the runtime stitcher
idempotent.

`flow_kind` and `data_flow_confirmed` are unchanged at the schema
level. `flow_kind` defaults to `"control"` (already the default).
`data_flow_confirmed` defaults to `NULL` (already nullable). What
changes is what the Layer 1a code writes: `flow_kind = "control"`,
`data_flow_confirmed = NULL`.

## Consequences

### Positive

1. **The AST layer stops lying.** `data_edges_only = []` on a Layer 1a
   scan is the correct answer, not a failure. The report says so.
2. **`observed_by` is extensible.** Runtime, symbolic execution, manual
   review, third-party tools — each adds a prefix. No schema change
   for a new confirmation source.
3. **The runtime stitcher has a schema to write into.** A runtime
   observation is "this (file, line, name) was executed, and data
   reached this sink". The graph can represent that as
   `observed_by` gains `"runtime"` on the matching node and edge.
4. **Classification is replaceable per project.** A user detector is
   a `FrameworkDetector` — the same interface, loaded from a path.
   No separate "project classifier" concept.
5. **Scan policy is reproducible.** "We ran with this `scan.yaml`" is
   a fact; "we ran with these flags" is not.
6. **The prompt can weigh provenance.** `observed_by = ["ast"]` +
   `flow_kind = "control"` is weaker evidence than
   `observed_by = ["ast", "runtime"]` + `flow_kind = "data"`. The
   LLM sees both.
7. **lethal_trifecta** is a valid AST signal. It is a node property, 
   computed from capabilities, and it does not depend on Layer 2. The 
   flag fires on the AST layer when the combination is present; runtime 
   strengthens the path evidence around it, not the flag.

### Negative

1. **`flow/` becomes dormant on Layer 1a.** The analyzers run, but
   their output is not stored until Layer 2 exists. This is a
   temporary state: `flow/` is the mechanism Layer 2 uses, and it is
   tested independently. But until Layer 2 lands, `flow/` has no
   producer that writes its output.
2. **The report is less informative on an AST-only scan.** No `data`
   edges, no `lethal_trifecta` (which requires `reads_untrusted` +
   secrets + egress on one node — the read side is available, but
   the combination needs runtime to confirm the egress path).
3. **`--clean` semantics change.** It no longer deletes `config/`.
   This is a fix, but it is a behavior change users may notice.
4. **The class-A heuristics are gone.** A project not covered by a
   framework detector, a user detector, or the LLM classifier
   produces fewer nodes than before. This is intentional: the old
   behavior was FinBot-specific and wrong on other projects.

### Neutral

1. **`flow_kind_for` remains.** The mapping is the single
   implementation of ADR-0015 decision 3; it is used by Layer 2 and
   by tests.
2. **`FlowDecision` remains.** Same reason.
3. **`data_flow_confirmed` values are unchanged.** The six values and
   `NULL` are still the vocabulary. Only the producer changes.
4. **lethal_trifecta** remains a node attribute. It is computed from 
   capabilities and written by **LethalTrifectaStage**. The combination 
   is valid on the AST layer: a node either has reads_untrusted + 
   reads_secrets/reads_env + egress or it does not, and capabilities 
   answer that question without runtime. Runtime adds confirmation that 
   the path from such a node to a sink carries data; it does not add the
   flag itself. A rare signal that fires is stronger than a common one 
   that always fires — the flag is kept because it is cheap and because,
   in practice, it surfaces during development even on targets where no 
   corpus has produced it yet.

## Deferred

1. **Layer 2 implementation.** ADR-0016 defines the schema; the
   runtime module is separate work (`runtime/python/`).
2. **`observed_by` on `chain_groups`.** Chain groups are pairs of
   chains through an untrusted source. Their `observed_by` is the
   union of their constituent edges' `observed_by`, computed on read,
   not stored. Deferred until a runtime run produces a group worth
   storing.
3. **Log rotation on `--clean`.** `logs.keep_archives` is in
   `scan.yaml`, but reading the config before `clean()` is a larger
   change than it looks. Deferred to a separate backlog item.
4. **`validated_kind` on chains.** Layer 3 validation currently
   checks existence only. Semantic validation (direction, order,
   roles) is separate work; when it lands, `validated` gains a
   `validated_kind` field (`existence` | `semantic`). ADR-0016 does
   not decide the field's name or values.
5. **LLM classifier prompt.** ADR-0016 decides that the classifier
   exists and how it is controlled. The prompt itself is separate
   work (`parsing/llm_classifier/prompt.py`), and it is versioned
   independently of `PROMPT_VERSION` (which is for chain evaluation).
6. **User detector loading.** `framework_detectors/loader.py` is
   specified in this ADR (the interface), but its implementation is
   a separate task.

1. `observed_by` is a JSON array on every node and edge. Default
   `["ast"]`. Required.
2. `FlowKindStage` sets `flow_kind = "control"` on every AST edge and
   does not write `data_flow_confirmed`.

   Layer 2.
