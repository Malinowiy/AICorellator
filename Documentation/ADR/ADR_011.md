# ADR-0011: Framework Detectors

**Status:** Accepted
**Date:** 2026-10-13
**Context:** Phase 1 — Classification and normalization

---

## Context

Classification by name and path is hardcoded for FinBot-style projects. Agents are classes whose name ends in `Agent`. MCP servers live under `mcp/servers/`. Agent calls are functions named `delegate_to_*` or `run_*_agent`. This works for one project layout and fails for every other.

On LangChain 1.0, LangGraph, CrewAI, AutoGen, OpenAI Agents SDK, and FastMCP, the graph is nearly empty or entirely absent. The classifiers do not recognize the imports, do not understand the decorators, and do not see the framework-specific call patterns.

The project needs classification that works across frameworks, resists obfuscation, and degrades gracefully when a framework is unknown.

---

## Decision

**Three classification levels, with framework detectors as Level 1.**

1. **Level 1 — Framework detectors.** Exact detection for known SDKs. Per-file. Each detector recognizes one framework.
2. **Level 2 — Capability extraction.** AST-derived capabilities (ADR-0009). Framework-agnostic.
3. **Level 3 — Name-based heuristics.** Class names, method names, file paths. The original FinBot-tuned rules.

If Levels 1 and 2 produce nothing for a symbol, Level 3 decides. If Level 3 also produces nothing, the symbol is not classified.

The three levels are not a pipeline inside one function. Level 1 runs as a separate pass over the manifest, producing detector nodes and edges. Level 2 runs as another separate pass, producing per-symbol capabilities. Level 3 runs inside the normalizer, with Level 2 capabilities supplied as input. The normalizer merges Level 1 output with Level 3 output.

When both a detector and Level 3 produce a node with the same name and source file, the detector node is authoritative for kind. Capabilities are merged, not replaced.

---

## Level 1: Framework Detectors

One detector per framework. Detection is by imports and API patterns.

The frameworks and their status:

| Framework | Detection signature | What it finds | Status |
|---|---|---|---|
| LangChain | `langchain.agents`, `AgentExecutor`, `create_agent` | Agents, tools, LLM clients | Implemented |
| LangGraph | `langgraph.graph`, `StateGraph` | Graph nodes, graph edges, conditional routing, entry points | Implemented |
| OpenAI Agents SDK | `openai.agents`, `Agent`, `Runner` | Agents, handoffs, guardrails | Planned |
| FastMCP | `fastmcp`, `FastMCP` | MCP servers, tools | Planned |
| MCP SDK (Python) | `mcp`, `Server`, `@server.tool()` | MCP servers, tools | Planned |
| CrewAI | `crewai`, `Agent`, `Task`, `Crew` | Agents, tasks, tools | Deferred |
| AutoGen | `autogen`, `ConversableAgent` | Agents, group chats | Deferred |
| Semantic Kernel | `semantic_kernel` | Plugins, functions, planners | Deferred |
| MCP SDK (TypeScript) | `@modelcontextprotocol/sdk` | Same as Python, for TS | Deferred |

### What Level 1 gives

- **Exact classification.** Imports cannot be obfuscated away. If a file imports `langchain.agents`, the detector knows it.
- **Framework semantics.** The detector knows that `AgentExecutor` is an agent, not just a class whose name ends in `Agent`.
- **Provenance.** Every node produced by a detector carries a `framework` attribute. Downstream components can reason about which framework a node came from.
- **Capabilities on tool nodes.** A function decorated with `@tool` has its body scanned for capabilities. A tool that calls `exec` gets the `executes_code` capability, attached where it belongs.

### Per-file contract

Detectors are **per-file by design**. A detector receives one file path, one AST, and one source string, and returns nodes and edges from that file alone.

This is deliberate:

- No import resolution inside the detector. A detector does not read other files.
- No global state. A detector is safe to run in parallel with others.
- No dependency on manifest layout. A detector works for any target structure.
- Adding a detector means writing one file and registering it. Nothing else changes.

**Cross-file edges are not the detector's job.** They are resolved by the normalizer, per ADR-0013.

### Loading and selection

Detectors are loaded by name. The user selects which frameworks to enable for a scan. If a detector is not enabled, its nodes are not produced.

### Version support

Each detector declares a supported version range for its framework. If the detected framework version is outside the range, a warning is logged and detection proceeds at the user's risk. This is a deliberate choice over silent failure: a version mismatch does not block the scan, but the analyst is told.

### Registry

The detector registry maps names to detector classes. Adding a detector is one line in the registry.

## Level 2: Capability Extraction

From ADR-0009. Capabilities are derived from AST calls, not from names.

Level 2 runs as a separate pass over the manifest. Its output is a per-file capability map: for each file, a list of symbols and the capabilities exercised by each symbol.

Capabilities are passed to the normalizer and attached to nodes. They are also used by Level 3 to override name-based decisions:

- A class with `executes_code` or `executes_shell` is a sink, regardless of its name.
- A class with `calls_llm` is an LLM endpoint or an agent, regardless of its name.

---

## Level 3: Name-Based Heuristics

Implemented in `parsing/classification.py`. Three entry points: classification of a class, of a method, and of a file (for MCP servers).

The heuristics are tuned against FinBot CTF. They are intentionally conservative: false positives are cheaper than false negatives, because Phase 3 filters noise. A missed agent is worse than a spurious one.

Level 3 is the fallback. It runs in the normalizer after detector merge, with Level 2 capabilities supplied as input.

**Note on the original ADR.** An earlier draft described a `structural_heuristics.py` module as Level 3, and a `classification.py` orchestrator that tried Levels 1, then 2, then 3 in sequence. Neither was implemented. The actual Level 3 is `classification.py` itself, and orchestration is done by the normalizer, not by `classification.py`. The draft has been removed.

---

## Cross-File Resolution

Cross-file resolution is **not part of Level 1**. It is a normalizer concern, invoked after detector merge.

See **ADR-0013** for the full design. Summary:

- The normalizer resolves agent-to-tool edges across files by reading per-file imports.
- The normalizer resolves entry-point-to-agent edges by linking entry points with no outgoing delegation edge to the single framework agent in the project.
- A new stored edge kind, `uses_tool`, is introduced for agent-to-tool edges.

The rationale for placing this in the normalizer, not in detectors:

- The normalizer already receives the full manifest and all detector output.
- Detectors remain per-file, preserving the Level 1 contract.
- False positives are accepted (ADR-0009), so a coarse resolution is sufficient.

## Architecture

The parsing module is organized as follows:

- `framework_detectors/base.py` — the `FrameworkDetector` interface and the `DetectionResult` container.
- `framework_detectors/langchain.py` — the LangChain detector (implemented).
- `framework_detectors/langgraph.py` — the LangGraph detector (implemented).
- `framework_detectors/registry.py` — name-to-class mapping.
- `framework_detectors/cross_file.py` — cross-file edge resolution (ADR-0013).
- `capability_extractor.py` — Level 2 (ADR-0009).
- `classification.py` — Level 3, name-based heuristics.
- `detectors_runner.py` — orchestrates Level 1 across a manifest.
- `ast_normalizer.py` — merges Levels 1, 2, and 3 into a `GraphDelta`.

---

## Implementation Order

1. LangChain + LangGraph — implemented.
2. Cross-file resolution — implemented (ADR-0013).
3. Capability-based sink enumeration — implemented (ADR-0014).
4. OpenAI Agents SDK — next.
5. FastMCP + FastAPI entry points — after OpenAI Agents SDK.
6. MCP SDK (Python) — after FastMCP.
7. Further detectors on request.

The order prioritizes frameworks with the most real-world targets. LangChain and LangGraph dominate current AI infrastructure. OpenAI Agents SDK is rising. FastMCP and MCP Python SDK are foundational for MCP-based targets.

---

## Testing

Each detector is tested at three levels:

1. **Unit tests with inline code strings.** Short snippets parsed in-memory. Assertions on the resulting nodes and edges. Fast, deterministic, no fixtures on disk.
2. **Integration test with a synthetic project.** One shared fixture containing an agent with real capabilities. Used by the pipeline test.
3. **Integration test with a real target.** FinBot CTF and NMB are scanned manually to verify end-to-end behavior.

An earlier draft proposed generating a synthetic project per framework. This has been simplified: unit tests use inline strings, and one shared fixture covers the pipeline. Generating and maintaining one fixture per framework is a burden that has not yet proven necessary.

---

## Consequences

### Positive

1. The system works across different AI frameworks.
2. Obfuscation-resistant. Imports cannot be hidden.
3. Framework semantics are captured.
4. Detectors are isolated. Adding one means one file plus one registry line.
5. Cross-file resolution is layered on top without touching detectors.
6. Capabilities are preserved across kind overrides.

### Negative

1. Each detector is a separate module of a few hundred lines.
2. Framework APIs change; detectors require maintenance.
3. Version drift requires warnings, not silent failures.
4. Cross-file resolution uses coarse heuristics. Accepted (ADR-0009).

### Neutral

1. Fallback to name-based heuristics remains.
2. Framework provenance is an attribute on detector nodes; it does not affect node kind.
3. `uses_tool` is a stored edge kind (ADR-0013).

---

## Not in Scope

- Detectors for **unknown** custom frameworks.
- **Runtime** detection (static only, ADR-0001).
- **Cross-file dataflow** for route-to-agent matching when there are multiple agents (deferred, ADR-0013).

---

## Decision

1. **Level 1** — framework detectors, per-file, pluggable via registry.
2. **Level 2** — capability extraction, framework-agnostic.
3. **Level 3** — name-based heuristics in `classification.py`, used as fallback.
4. **Cross-file resolution** — normalizer concern, per ADR-0013.
5. **Implementation order** — LangChain/LangGraph (done), OpenAI Agents SDK, FastMCP, MCP Python SDK.
6. **Testing** — inline code strings for unit tests, one shared fixture for pipeline tests.
