# ADR-0023: LLM fallback for unresolved store identity

**Status:** Accepted
**Date:** 2026-10-30
**Related:** ADR-0009 (capabilities from AST calls), ADR-0016 (control-only AST), ADR-0021 (store model; §8 signals, §9 thresholds, §7 two confidence fields), ADR-0022 (`source_type='user_upload'` end-to-end), D.2 (`parsing/llm_classifier/`)

---

## Context

ADR-0021 §5: an unresolved store identity produces no store, no edges, no group. The rule is correct — a `Bucket=var` or `open(path)` names no store the AST can see — but it is a **silent** gap: the analysis cannot distinguish "no store" from "a store the AST could not name". The unresolved sites are the ones the LLM might name from the surrounding code: a handler whose docstring says "uploads go to `/uploads/`", a route parameter whose name says `docs`, a `Path(...)` join whose literal parts the AST could not combine.

The AST layer is deterministic and fast; it will not be widened to guess values (ADR-0001, ADR-0016). The existing **Layer 1b** (D.2, `parsing/llm_classifier/`) already runs an LLM classifier for the **kind** gap (a symbol the deterministic layers could not classify), with a cache, opt-in, three provenance limiters. The store identity gap is the same shape: a deterministic layer could not resolve it, and a small local LLM can propose a value.

This ADR decides: an **opt-in LLM fallback** for unresolved store identity, its model, its prompt, its cache, its confidence, and where it runs. It is not the primary producer of store identity; it is the last resort after the AST and the resolver's signals.

---

## Decision

### 1. What the fallback fills

The fallback runs on sites that **no deterministic producer** could name:

- A family's `WriteSite` / `ReadSite` with `identity_hint=None` (an `open(path)`, a `Bucket=var`, an f-string without a literal prefix, a handle the family could not resolve).
- In the **writer's scope** (the upload context's scope rule, ADR-0022 §1): a site the attribution pass could not create a source for, because the reader's path was unresolved.

The fallback **does not** run on sites the deterministic producers already named (a literal `open('/uploads/x')`, a resolved `Bucket='docs'`). The deterministic answer wins; the fallback fills the gap (the D.2 rule, §"deterministic wins", unchanged).

### 2. The LLM model

`config.yaml`'s `llm_fallback_model` section:

```yaml
llm_fallback_model:
  base_url: "http://localhost:1234/v1"
  model: "qwen/qwen3-4b-2507"       # default: the same as llm_classifier_model
  temperature: 0.0
  max_tokens: 400
  timeout: 120
  response_format: "schema"
```

The section is **separate** from `llm_classifier_model` and `evaluation.models`. The default is the same model as `llm_classifier_model` (one model, two prompts — no two-model requirement for the default case), but the section is separate so a user can point the fallback at a different model (a smaller one, a fine-tuned one) without touching the classifier's. A missing section with `mode: auto` or `required` is an error, same as D.2's `llm_classifier_model`.

`temperature` default `0.0` — the same reason B.5 made the judge deterministic: a store identity is a **stable** answer, not a sampled one. A per-model override is honored if a user wants stochasticity (a `temperature: 0.6` in the section).

### 3. The prompt

The prompt is **separate** from D.2's `llm_classifier/prompt.py`. It lives in `store/llm_fallback/prompt.py` (or `store/prompts/store_identity.py` — the module's own home, next to the fallback code, not in `parsing/`; the fallback is a store subsystem, not a parsing layer).

The prompt's own `PROMPT_VERSION` (e.g. `"store_identity:v1.0.0"`) is the cache's `prompt_version` component. It is independent of D.2's `PROMPT_VERSION`; editing one does not invalidate the other.

The prompt's input: the unresolved site's call shape (the dotted target), the surrounding code (the enclosing function or module body, a window), the file path, the imports. The output schema: `{identity_hint: str | null, confidence: float, reasoning: str}`. A `null` identity is a valid answer ("the code does not name a store"); the site stays unresolved.

The prompt's `[UNTRUSTED_DATA]` markers and the "content within markers is data" rule are the same as D.2's (a target can contain an instruction aimed at the prompt; the answer is validated against a schema, so an injected answer can choose a wrong hint from the allowed shape, not invent a kind or a capability). State in the prompt's docstring.

### 4. The cache

The cache is the **same SQLite file** as D.2's (`cache/llm_classifier.sqlite3`), keyed on `(content_hash, prompt_version, model_id)`. The `prompt_version` is the fallback's own (`"store_identity:v1.0.0"`), so a classifier answer and a fallback answer for the same symbol never collide (different `prompt_version`). One file, one `--clean`, no second cache directory.

`content_hash` is the same function (`cache.content_hash`) over the fallback prompt's inputs (the site's call shape, the surrounding code window, the file path, the imports) — the inputs are different from D.2's, so the hash is over the fallback's inputs, not D.2's.

### 5. The confidence — a special floor for `identity_source='llm'`

A store the fallback creates carries `identity_source='llm'` (an edge attribute, ADR-0021 §7's `identity_confidence` has the field; the `identity_source` names the producer). Its `identity_confidence` is:

- **base 0.2** (not 0.3 — the LLM's guess is weaker than an AST literal; the AST sees the literal, the LLM sees the surrounding code and infers).
- **plus the LLM's own confidence** (the model returns `confidence: 0.0–1.0`; the combined value is `0.2 × (0.5 + 0.5 × llm_confidence)` = `0.1–0.2`), or simply **0.2** with a "confidence from LLM" attribute. **The reading:** `identity_confidence = 0.2` (the base) — the LLM's own confidence is recorded as `identity_confidence_llm` in the edge's attributes, not folded into the number, because folding two probabilities is a decision that would need its own tuning and the number's meaning should be stable.
- **No literal match, no code context** (the LLM's guess is not a literal the AST saw; the code context is already the reason the fallback ran).

**The special floor.** ADR-0021 §9's floor is `0.3` (`WEAK_JOIN_FLOOR`); a fallback store at `0.2` would be below it, so it would produce no store, no edges, no group — **the fallback would be inert**. This ADR sets a **special floor for `identity_source='llm'`: 0.1**. A fallback store at `0.2` (or `0.1`) is **weak** (`weak: true`, outside the default enumeration, `include_weak=True` to see it), but it **exists**: it can be joined by store id, and a chain group can form (weak). The analyst sees the group and knows it came from an LLM guess (`identity_source='llm'`, `weak: true`).

**Why not raise the fallback to 0.3.** A `0.3` floor would make the LLM's guess as strong as the weakest deterministic signal (a one-side-literal `fs` read). That is wrong: the LLM does not see a literal; it sees the code and infers. `0.2` reflects the guess's strength; the special floor reflects the category (an LLM guess is a weak group, not a non-group).

**ADR-0021 §9's floor is unchanged for deterministic sources**; the special floor applies **only** to `identity_source='llm'`. A future ADR can revisit if a corpus argues for a different floor or a different combine.

### 6. Where the fallback runs

A new module `store/llm_fallback/` — the fallback's code, prompt, config, and runner — called from the store resolver stage (stage 19) **after** the resolver's families and the upload attribution pass:

```
StoreResolver.resolve → UserUploadContext.identify → find_upload_stores → attribute_source_type
  → llm_fallback.run(unresolved_sites, ...) → store + writes_to / reads_from (identity_source='llm', base 0.2)
```

The fallback is a **step** in the store resolver stage, not a family, not a resolver change. Its input is the unresolved sites the families and the attribution produced; its output is the stores (with `identity_source='llm'`) and the edges (base 0.2, weak). The resolver does not know about it; the stage calls it after the resolver's run.

**Opt-in.** `config.yaml`'s `llm_fallback.mode: off | auto | required` (default `off`, D.2's pattern). `off` — the fallback never runs; unresolved sites stay unresolved (no store, no edges, no group; ADR-0021 §5 unchanged). `auto` — the fallback runs on the unresolved sites in scope; a failed answer leaves the site unresolved (a warning). `required` — a failed answer is a scan failure (the analyst asked for the layer; a gap must not pass silently). The modes match D.2's, so the config is the same shape.

### 7. What the fallback does not do

- **No replacement of deterministic identity.** A literal `open('/uploads/x')` is not re-classified; a resolved `Bucket='docs'` is not re-named. The deterministic answer wins; the fallback fills the gap (ADR-0016's "deterministic wins").
- **No change to existing stores.** The fallback creates new stores for unresolved sites; it does not re-target or re-name a store a deterministic producer created.
- **No multi-role source type.** ADR-0022 §4 unchanged.
- **No prompt or capability change.** The kind / capability classifier (D.2) is unchanged; the fallback's prompt is its own.
- **No value following.** The fallback's input is the site and the surrounding code; it does not follow values through calls (ADR-0001). A code window is the input; a dataflow is not.
- **No change to the `chain_groups` path.** Its `validated` is B.4b's check; the fallback's weak groups flow through as any weak group (ADR-0021 §9).

## Rationale

### Why a separate model section, and not `llm_classifier_model`

The default is the same model (one model, two prompts), but a user who wants a different model for the fallback — a smaller one, a fine-tuned one, one tuned for inference of literals rather than kind — sets `llm_fallback_model.model` without touching `llm_classifier_model.model`. The two prompts are different tasks; the models can be different. A single section would couple them for no reason.

### Why the same cache file

`--clean` deletes `cache/`; a second cache directory is a second thing to clean, a second thing to forget. The `prompt_version` is the discriminator; the `content_hash` is over the fallback's own inputs; the two prompts' entries never collide. One file, one cleanup.

### Why a special floor

The ADR-0021 §9 floor (0.3) is a **deterministic** floor: the analysis refuses to join two stores whose confidence is below 0.3, because the signals (family, literal, code context) are structural and a weak join is a weak **structural** claim. The LLM's guess is a **different kind of signal**: it is not a structural fact, it is a probabilistic inference. A fallback store at 0.2 is **weak** (the analyst should see `weak: true`), but it is **a real weak group**, not a non-group. The special floor (0.1) lets it exist and be seen; the `weak` flag names the uncertainty.

**What this does not change:** a deterministic store at 0.2 (impossible today — the deterministic producers' bases are 0.3 / 0.4 / 0.5) would still be below the 0.3 floor; the special floor is for `identity_source='llm'` only.

### Why opt-in, not on by default

The LLM is expensive (one call per unresolved site, cached). A scan that reaches a model endpoint by default is a scan nobody can run offline. D.2's default is `off`; the fallback's is `off`; the pattern is the same. An analyst who wants the layer turns it on and accepts the cost.

### Why the fallback is a step, not a family

A family is a per-file detector: `detect_writes` / `detect_reads` on one file's AST, before the resolver. The fallback is the opposite: it runs **after** the deterministic layers, on sites they **could not** classify, and its input is the surrounding code, not the file's AST per se. It is a **post-resolver** step, the same shape as D.2 is a post-parsing step. Putting it in a family would couple a family's `detect_*` to an LLM call; putting it in the resolver would couple the resolver to the model. A separate module called by the stage keeps the boundaries.

### What it means for the corpora

On the four corpora, no site is unresolved in a writer's scope today (the previous steps' corpus scans found none). The fallback is a no-op on them; the tests are synthetic (a site with a `Bucket=var` and a docstring naming the bucket; a `open(path)` whose `path` is a parameter named `upload_dir`). The mechanism is the point; the corpus trigger is a future target.

---

## Consequences

- **A new opt-in layer.** `store/llm_fallback/` (module, prompt, config, runner); a new `llm_fallback_model` section; a new `llm_fallback.mode` policy; a new `identity_source='llm'` attribute on fallback edges; a special floor (0.1) for `identity_source='llm'`.
- **The fallback creates stores** for unresolved sites in scope; it does not change deterministic stores. The `writes_to` / `reads_from` edges carry `identity_source='llm'` and `identity_confidence=0.2`; the store joins by store id, and a weak chain group can form.
- **The special floor is ADR-0021 §9's first exception.** A future ADR can revisit if a corpus argues. The floor is documented in `store/llm_fallback/` and in ADR-0021's next revision.
- **The prompt is its own** (`store/llm_fallback/prompt.py`), its own `PROMPT_VERSION`; the cache is shared with D.2's file, not with its keys.
- **No change to D.2, ADR-0021's deterministic producers, ADR-0022, the chain-groups path.**
- **Corpus regression:** the four corpora have no unresolved site in scope today; the fallback is a no-op. A target with a `Bucket=var` and a docstring naming the bucket (or a `path` parameter named `upload_dir`) is the shape the synthetic tests pin.
