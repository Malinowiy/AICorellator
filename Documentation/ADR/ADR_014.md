# ADR-0014: Sink by Capabilities in Chain Enumeration

**Status:** Accepted
**Date:** 2026-10-13
**Context:** Phase 1 — Graph query, Phase 3 — Chain enumeration

---

## Context

Chain enumeration in the query layer finds structural paths from entry points to sinks. The original implementation matched sinks by node kind: a node was a sink if its kind was `sink`.

This works when a dangerous action is a method whose name matches a known pattern — `execute_script`, `upload_file`, and similar. The method classifier assigns `kind = "sink"` to such methods, and chain enumeration finds them.

It fails when a dangerous action is exposed through a **tool** node.

Real example from NMB (LangChain 1.0): a function decorated as a tool calls `exec` on its argument. The capability extractor (ADR-0009) sees the `exec` call and assigns the `executes_code` capability to the function. The method classifier sees `executes_code` in the sink capability set and would classify the function as a sink. But the framework detector sees the `@tool` decorator and creates a node of kind `tool` with the same name and source file.

Merge by name and source file makes the detector node authoritative: the node becomes `tool`, not `sink`. Its capabilities include `executes_code` — the capability is preserved, only the kind changes.

The result: the node is a tool with `executes_code`. Chain enumeration does not see it as a sink. No chain reaches it. Before this ADR, the NMB graph had 17 edges and 0 chains.

This is a semantic mismatch, not a modeling bug. The node **is** a tool: it is decorated, registered, and callable. But it **also** exercises a dangerous capability. Both facts are true. Chain enumeration must see the second.

---

## Considered Options

### Option A: Change the node kind back to `sink` after merge

Force the merged node's kind to `sink` when it has a sink capability.

**Rejected.** It breaks the detector's authority (ADR-0011). A tool decorated with `@tool` is a tool. Changing its kind to `sink` loses information: the LLM in Phase 3 no longer knows it is a tool, and cannot reason about an agent-to-tool-to-sink chain.

### Option B: Create a separate sink node alongside the tool node

Emit two nodes — a tool node and a sink node with the same name — and an edge between them.

**Rejected.** This doubles the node count for every dangerous tool and introduces an artificial edge that carries no meaning. It also breaks the name-and-source-file uniqueness used elsewhere in the normalizer.

### Option C: Treat capability as an alternative sink condition in chain enumeration

Extend chain enumeration to accept nodes with dangerous capabilities as valid endpoints, in addition to nodes of kind `sink`.

**Accepted.**

---

## Decision

**Adopt Option C.**

Chain enumeration now computes its sink set as the union of:

1. Nodes whose kind is in the sink-kind list (default: `sink`).
2. Nodes whose `capabilities` include at least one capability from the sink capability set.

The capability check is implemented as a helper on the query layer. It loads active nodes and filters in Python. At the graph sizes the project targets — thousands of nodes, hundreds of chains — this is fast enough, and it is simpler than SQL JSON extraction.

### Sink capability set

The set is defined once, in the patterns module, and imported by both the classifier and the query layer:

    executes_code
    executes_shell
    writes_filesystem
    writes_db
    http_egress

This is the single source of truth for "what counts as a sink". The classifier uses it to classify symbols. The query layer uses it to decide which nodes terminate a chain. Adding a new sink capability means touching one file.

`http_egress` was added to the set as part of this ADR. It was absent from the original classifier set — an oversight, since ADR-0009 explicitly lists exfiltration as a sink capability. Its inclusion is a correctness fix, not a scope expansion.

### Capability sets move to the patterns module

The four capability sets — sink, agent, LLM-endpoint, and tool — are moved from the classifier to the patterns module. Rationale: they are data, not logic. The patterns module is the registry of everything the project knows about AI systems. The classification logic stays in the classifier; the sets move to the registry.

This also removes a duplicate definition of the sink set that would otherwise exist between the classifier and the query layer.

---

## Rationale

- **Capabilities are first-class (ADR-0009).** A node's kind describes what it is; its capabilities describe what it does. Chain enumeration cares about what a node does at the end of a chain. A tool that executes code is as dangerous as a sink method that executes code.
- **No information is lost.** The node stays a tool with `executes_code`. The LLM in Phase 3 sees both facts: it is a tool, and it executes code. This is exactly the reasoning the ensemble needs.
- **The change is small and localized.** Chain enumeration gains one call and one helper. No schema change, no new edge kind, no detector change.
- **The result is measurable.** On NMB: 17 edges, 8 chains (was 0). On FinBot: 91 edges, 180 chains, unchanged. The `http_egress` addition did not add sinks in FinBot, because FinBot's dangerous methods already matched by name.

---

## Consequences

### Positive

1. Tools with dangerous capabilities are valid chain endpoints.
2. Node kind stays accurate: a tool is a tool.
3. Capabilities remain first-class for Phase 3 reasoning.
4. A single source of truth for sink capabilities.
5. `http_egress` is now correctly treated as a sink capability, matching ADR-0009.

### Negative

1. More chains. A project with many `http_egress` tools will produce more chains. Accepted: the LLM ensemble in Phase 3 prioritizes and filters, and the point of Phase 1 is to enumerate candidates, not to prune them.
2. The capability filter loads all active nodes and filters in Python. For graphs with tens of thousands of nodes this may be slow. Accepted for now; the SQL JSON extraction alternative is more complex and not obviously faster at current graph sizes.

### Neutral

1. No schema change.
2. No new edge kind.
3. The classifier shrinks by a few dozen lines; the patterns module grows by a similar amount.

---

## Deferred

1. **Capability-based entry points.** Currently entry points are matched by kind. A node with the `http_ingress` capability might also be an entry point. Deferred; no current target needs it.
2. **Capability-based intermediate node matching.** Chains might need to pass through specific capabilities — for example, `reads_untrusted` for indirect prompt injection. Deferred to ADR-0010 implementation.
3. **Indexed capability search.** Adding a SQLite index on the JSON-extracted capabilities to speed up the filter. Deferred; current graphs are small.

## Decision

1. Chain enumeration accepts nodes with sink capabilities as valid endpoints, in addition to nodes of kind `sink`.
2. The sink capability set lives in the patterns module, imported by both the classifier and the query layer.
3. `http_egress` is included in the sink capability set — a correctness fix relative to ADR-0009.
4. All four capability sets move to the patterns module.
