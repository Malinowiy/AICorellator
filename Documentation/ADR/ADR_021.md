# ADR-0021: Store as a graph entity, with probabilistic write/read links

**Status:** Accepted
**Date:** 2026-10-29
**Extends:** ADR-0015 (`flow_kind`; structural edges), ADR-0010 (chain groups)
**Related:** ADR-0009 (capabilities from AST calls), ADR-0012 (group scoring), ADR-0016 (control-only AST), ADR-0019 (guardrail weighting; the precedent for "signal, not filter")
**Revised:** 2026-10-29 — §1 corrected (family = technology, not source type), §12 extended (family modules and registry). See the "Revision note" below.

---

## Context

ADR-0010 models a chain group as a write chain and a read chain that meet at an **untrusted source**. The source is a **read site** — the place the AST sees a read (`retriever.invoke`, `client.list_tools`, `imap.search`) — and `untrusted_source_writers` (1.3a.1, extended by B.2) links a **writer** to that source by same-file, `parent_server`, or literal factory path.

This works for three families: `rag_corpus`, `email_inbox`, `mcp_tool_description`. The writer is a call site (`vectorstore.add_documents`, `smtp.sendmail`, `@mcp.tool()`), and the source is where the read happens; the edge between them is a structural fact the AST can see.

It does not work for `user_upload` (BACKLOG B.3), and B.3 is not the only case. **The store is an entity the current model does not have.** An upload handler writes into S3, a directory, or a database; a tool reads from the same place; the AST sees the write call and the read call, but **not** that the two call sites point at the same store. The write site is `s3.put_object(Bucket='docs', ...)`; the read site is `s3.get_object(Bucket=var, ...)`. Same family, different file, **store identity in the arguments** — the AST cannot match the two by file or by import, and matching by name (`Bucket`) is a class-A heuristic ADR-0016 removed.

Runtime does not close the gap either. A runtime run sees the value of `var` in that run; it does not see the write handler that was not invoked, or the read site that was not exercised. Moving the problem to Layer 2 with "it will be visible there" is the same mistake as "the AST will see it", deferred.

The honest answer is that **store identity is probabilistic from the AST**. Two call sites may write to and read from the same store; the AST has signals — the call shape (family), the literals in the arguments, the module the call lives in — and the signals combine into a **probability**, not a fact.

This ADR decides the model: a `store` node, `writes_to` and `reads_from` edges, `identity_confidence` on those edges, and a join in `find_chain_groups` by store id. The probability is stated; the analysis does not pretend it is certainty.

---

## Decision

### 1. `store` is a new node kind

A `store` node is a place write and read call sites point at. Its identity is `(family, identity_hint)`:

- **family** — the store `technology`: `fs, s3, db, ...` — how the store is reached, not what semantic role it plays. A closed set, one per family module (§12's "each family needs a write rule, a read rule, and the literals that name its store" — the rule and the module are the same unit). The **semantic role** is on the read site: `untrusted_source.source_type` (`user_upload` / `rag_corpus` / `email_inbox` / `mcp_tool_description`), unchanged. `mcp_tool_description` becomes `store('mcp_catalogue', '<name>')` in B.3c — `mcp_catalogue` is the **technology** (an MCP tool catalogue as a store), not a source type; the source type stays `mcp_tool_description`.
- **user_upload** is `not a family`. It is a `source type`: the semantic role of a read site. An upload handler that writes into `/uploads/` and a tool that reads from it are a `store('fs', '/uploads/')` pair; the `source_type='user_upload'` on the read site is what makes the pair "an upload" rather than "a cache". The store is the technology; the source type is the role.
- **identity_hint** — the literal that names the store within the family: `s3://docs/*` → `('s3', 'docs')`, `/uploads/` → `('fs', '/uploads/')`, `documents` → `('db', 'documents')`, `finmail` → `('mcp_catalogue', 'finmail')`. A literal from the writer's or the reader's argument. If neither side has a literal (both are parameters, f-strings, or unresolved), the store is **not created** — §5.

A `store` node carries no `identity_confidence`; it is an entity, and an entity is either in the graph or not. Confidence belongs to the links (§4).

The node's `attributes` carry the family and the literal identity hint. `name` is `<family>:<identity_hint>` (or `<family>:*` for a `store` reached without a literal on either side — see §5, an unresolved identity produces no store, so this form does not occur today; the rule is stated for completeness).

### 2. `writes_to` targets a `store`, not an `untrusted_source`

ADR-0010's `writes_to` goes `writer → untrusted_source`. ADR-0021 changes the target: `writes_to` goes `writer → store`, **for every family**.

`mcp_tool_description` migrates: the server that declares the catalogue writes to `store('mcp_catalogue', '<name>')`, and the catalogue read site (`client.list_tools`) connects to that store via `reads_from`. B.2's `writes_to → untrusted_source` is replaced by B.3c's migration.

`untrusted_source` is unchanged: it remains the read site, with its `source_type` and its `source_file`. It is connected to the store it reads from by `reads_from` (see §3). The `has_access_to` edge from `untrusted_source` to its reader (1.3a) is unchanged.

### 3. `reads_from` is a new edge kind

`reads_from` goes `store → untrusted_source`. Direction is the store's: the store **is** the place the read site reads from.

`reads_from` does not connect `store → reader`. That alternative is rejected because it **loses** `source_type`: the reader is an actor (`tool`, `agent`), and `source_type` (`rag_corpus` / `email_inbox` / `user_upload` / `mcp_tool_description`) belongs to the read site, not to the actor. `has_access_to` (1.3a) already connects `untrusted_source → reader`; adding `store → reader` would duplicate that edge and drop the `source_type` that `find_chain_groups` and ADR-0012 scoring depend on.

Cardinality: `store → untrusted_source` is N:1. Many read sites may read from one store; each read site is its own `untrusted_source` node.

### 4. `flow_kind` for `writes_to` and `reads_from` is `structural`

`writes_to` and `reads_from` are **declarations**, not paths. The AST sees a call site writes to a store and a read site reads from a store; it does not see a value pass between them. `structural` is the honest classification, and it matches ADR-0015 decision 5: a declaration, not something execution flows along.

`STRUCTURAL_EDGE_KINDS` (patterns.py) gains `writes_to` and `reads_from`: `{"guards", "writes_to", "reads_from"}`. `find_chains` does not traverse them; §6 says how `find_chain_groups` uses them without traversing.

`observed_by` on both edges is `["ast"]` (the AST is the producer; Layer 2 may add itself later). `data_flow_confirmed` is `NULL` — no traced data flow (ADR-0016, decision 3).

### 5. Unresolved identity produces no store

A store is identified by its literal. If neither the writer's argument nor the reader's argument yields a literal (both are parameters, f-strings, or unresolved names), **no store is created**, and no `writes_to` / `reads_from` edges are emitted for that pair. This is not a false negative to be worked around: "two call sites of the same family, neither naming a store" is not evidence of the same store, and matching them on family alone would link every `s3.put_object` to every `s3.get_object` in the project.

If **one** side has a literal and the other does not, the store is created from the literal side. The link's `identity_confidence` is lower (§7): the writer's literal names the store, the reader's unresolved argument **may** point at it, and the confidence reflects the uncertainty.

### 6. `find_chains` does not traverse `writes_to` / `reads_from`; `find_chain_groups` joins by store id

The two methods do different things, and the ADR states the difference explicitly:

- **`find_chains`** is a path traversal from an entry point to a sink. `structural` edges are not traversed (ADR-0015, decision 5). `writes_to` and `reads_from` do not appear on a chain. `find_chains` is unchanged.

- **`find_chain_groups`** is not a path traversal; it is a **join**. It enumerates a **write chain** (a path from an entry point to a store, following `writes_to` as the last hop) and a **read chain** (a path from an `untrusted_source` to a sink, following `has_access_to` and the reader), and joins the two **by store id**: the write chain's last node is a `store`; the read chain's first node's `untrusted_source` connects to that store via `reads_from`. The join is by store id, not by traversal.

  `find_chain_groups` **already** crosses `writes_to` today (B.2, 1.3a.1) — the write chain exists only through it. ADR-0021 keeps that shape: crossing `structural` edges is allowed in `find_chain_groups`, because it is a join of two enumerated chains by a shared anchor, not a traversal of an attack path. ADR-0015 decision 5 is about `find_chains`; it does not forbid `find_chain_groups` from reading a structural edge as the write chain's last hop.

  The **anchor** of a chain group becomes the **store**, not the `untrusted_source`. The `untrusted_source` is the read chain's first node, connected to the store by `reads_from`; the store is the shared node both chains meet at.

### 7. `identity_confidence` on `writes_to` and `reads_from`

Each of `writes_to` and `reads_from` carries `identity_confidence: float | None`, distinct from `Edge.confidence`:

- **`Edge.confidence`** is the existing field: how sure the analysis is that **the edge exists** — the writer calls the write site, the read site reads from the store. For a call site the AST parsed, `confidence = 1.0`. `upsert` takes `max`, as today; Layer 3 validation (ADR-0018) reads it for existence.
- **`Edge.identity_confidence`** is the new field: how sure the analysis is that **the store on this edge is the same store** the other edge points at. It is computed from signals (§8), it is the field the join and the threshold use, and it is `NULL` on every edge kind other than `writes_to` and `reads_from` (the field is not applicable elsewhere).

The two fields are **orthogonal in meaning and stored separately**: `Edge.confidence` is existence, `Edge.identity_confidence` is identity. `upsert` uses `max` for `confidence` (as today) and **combination** for `identity_confidence` (two independent signals combine as `1 − (1 − old) × (1 − new)`, capped at 0.99, so a second signal strengthens the link). Layer 3 does not read `identity_confidence`.

`find_chain_groups`'s join confidence is `min(w.identity_confidence, r.identity_confidence)` — the **weakest** link decides the pair's confidence. A pair is as strong as its weaker side.

### 8. How `identity_confidence` is computed

Three signals, each independent, combined by `1 − Π(1 − sᵢ)` over the signals, starting from a **base of 0.3** when family matches:

1. **Family match (gate, not signal).** Writer and reader are the same family. Different families → no link, no store, no edge. Family match does not raise confidence by itself; it opens the possibility.

2. **Literal match (signal).**
   - Both sides have a literal, and they are equal → **+0.6**.
   - Both sides have a literal, and they are different → **no link** (they name different stores).
   - One side has a literal, the other does not → **+0.2** (the reader may point at the writer's store; the AST does not know).
   - Neither side has a literal → no store, no link (§5).

3. **Code context (signal).**
   - Same module (`source_file` equal) → **+0.2**.
   - Shared wrapper module: writer and reader both import a module (`storage.py`, `s3_client.py`) that defines the client the store is reached through, or both call methods on a module-level client defined in one of them → **+0.3**.
   - Shared import path (writer's file imports the reader's file, or vice versa) → **+0.1**.
   - Nothing shared → **0**.

The combination is `1 − (1 − 0.3) × Π(1 − sᵢ)` over the signals present, capped at 0.99. The exact constants are a policy choice, stated here and re-tuned after the first corpora; the **mechanism** (independent signals, combination, base 0.3) is the decision. The constants live next to the compute (the stage that emits `writes_to` / `reads_from`), not in `config.yaml`; the thresholds (§9) are the configurable part.

### 9. Thresholds and weak groups

`store_confidence_threshold` (default `0.7` in `config.yaml`) is the boundary between **strong** and **weak** groups:

- **Strong:** join confidence ≥ `store_confidence_threshold`. In `find_chain_groups`'s default output.
- **Weak:** `0.3 ≤ join confidence < store_confidence_threshold`. In the graph, but **not** in the default `find_chain_groups` output. `find_chain_groups(include_weak=True)` includes them, and a weak group carries `weak: true` on its `ChainGroup` / `ChainGroupRecord`.
- **No link:** join confidence < `0.3`. No store, no edges, no group.

The `0.3` floor is a constant (the base of §8); the `0.7` threshold is `config.yaml`'s. Both are re-tunable; the mechanism (two boundaries, weak visible only on request) is the decision.

Weak groups reach the LLM only when explicitly requested. A weak group's payload carries `weak: true`, and the prompt says a weak link is evidence of a possible store, not of a store — the group's confidence is lower for that reason. The prompt rule is the B.4b pattern: a signal, not a filter.

### 10. `untrusted_source` and `source_type` are unchanged

`untrusted_source` remains the read site. `source_type` (`rag_corpus` / `email_inbox` / `user_upload` / `mcp_tool_description`) is on `untrusted_source`, not on `store`. `store.family` is on the store. `find_chain_groups` reads `source_type` from the source, and `store.family` from the store; the two are different facts about the same pair, and neither replaces the other.

`has_access_to` (`untrusted_source → reader`, 1.3a) is unchanged.

### 11. Migration: B.2's `writes_to → untrusted_source` becomes `writes_to → store`

B.2 shipped `writes_to → untrusted_source` for `rag_corpus` and `email_inbox`. ADR-0021 changes the target. The migration is B.3c:

- every `writes_to` edge's target becomes a `store` node;
- every family's write side, including `mcp_tool_description`'s, goes through `store`;
- `reads_from` is emitted from each `store` to the `untrusted_source` nodes that read from it;
- `find_chain_groups` joins by store id (§6).

B.3a (the mechanism) and B.3b (`user_upload` family) come before B.3c (the migration). The order is fixed: B.3c cannot land until the mechanism and the first family are in place, because the migration touches the existing families and must run against a model that already works for one.

### 12. What this ADR does not decide

- **Family set beyond `user_upload`.** `fs`, `s3`, `db` are named as examples; the first family is `user_upload`'s (B.3b). Each family needs a write rule, a read rule, and the literals that name its store. Adding a family is a separate item.
- **Runtime enrichment of `identity_confidence`.** Layer 2 (Phase C) may observe values and raise or lower a link's confidence. The `identity_confidence` field is the hook; how Layer 2 writes it is Phase C's ADR.
- **`store` node in the report.** Whether `report.md` shows stores, and how, is not decided here. The bundle's `chain_groups.json` carries the store reference and the link confidence, because the group's payload needs them; the Markdown view is a separate decision.
- **`store` for a non-upload, non-RAG, non-mail, non-MCP place.** A cache, a message queue, an artifact registry — each would be its own family. Not in scope.
- **Store family modules and registry**. Each family is a module with a `detect_writes` / `detect_reads` interface, registered in a `registry.py` — the framework-detector shape (ADR-0011). The `shape` is decided here; the first module (`fs`) and the registry are B.3b-core and B.3b-fs. Adding a family is a file plus a line, not a change to the core.

### 13. What does not change

- `find_chains` and its traversal. `structural` edges are not traversed (ADR-0015 decision 5).
- `untrusted_source`, `source_type`, `has_access_to` (1.3a).
- `classification.py`, `schema.sql`, `graph/models.py` — except for the two new edge kinds and the one new node kind, each of which is a new value in the existing CHECK constraints.
- The read rules, `untrusted_sources.py`, the prompt, the evaluator (B.4b's payload is the natural place for `weak: true`, and that lands in B.3c's report work or a separate small step).
- `find_chains`'s `data_edges_only`, the `observed_by` rule, the `data_flow_confirmed = NULL` rule.

## Rationale

### Why a store node, and not an attribute on `untrusted_source`

The store is the entity the write side and the read side share. An attribute on `untrusted_source` cannot carry it: two read sites from the same store would be two `untrusted_source` nodes with the same attribute, and the write side would have to link to both, which makes the store an **implicit** join key — the same thing the AST currently lacks, hidden in an attribute. A node makes it explicit; the join is by a node id, and the graph has one store for `s3://docs/*`, not one per read site.

### Why `writes_to` changes target for every family

Two target kinds on one edge kind (`untrusted_source` for `mcp_tool_description`, `store` for the rest) would be a **two-model** graph: an old model for one family, a new model for the rest. Every consumer would need to know both, and the "is this write's target a store or a source" question would be answered by `edge.kind`-plus-family, not by `edge.kind`. One model, one target, one join.

### Why `structural` and not `data`

`data` is Layer 2's (ADR-0016, decision 3). The AST does not see a value pass from a writer to a store to a reader; it sees a write call and a read call and **reasons** about whether they point at the same place. That reasoning is `structural` — a declaration about a place, not a traced path. `control` is "X calls Y"; a writer does not call a store. `structural` is the classification that matches the claim.

### Why `find_chain_groups` joins by id, and does not traverse

`find_chain_groups` already crosses `writes_to` (the write chain's last hop). It is not a path from entry to sink; it is a **pair** of paths that meet at a shared node. ADR-0015 decision 5 ("structural edges are not traversed") is about `find_chains`, and `find_chain_groups` predates it as a different shape — the pair — and uses `writes_to` as the write chain's terminating hop. ADR-0021 continues that: the store is the shared node the pair meets at, and the join is by node id. A traversal would put a store on a path from entry to sink, which is the shape ADR-0015 decision 5 forbids. A join puts a store **between** two paths, which is what a chain group is.

### Why two confidence fields

`Edge.confidence` (does the edge exist) and `Edge.identity_confidence` (is this the same store) answer different questions for different consumers: Layer 3 reads `confidence`; the group join reads `identity_confidence`; `upsert` treats them differently (max vs combination). One field would conflate them, and the conflation would be invisible until a consumer confused the two — Layer 3 validating a link's identity, or the join using existence. Two fields make the distinction explicit.

### Why the weakest link decides the pair

A pair is as strong as its weaker side. `min` reads as "the pair cannot be stronger than the side the analysis is least sure about", which is the correct shape for a probabilistic join: a writer with a literal and a reader with a parameter is a **weaker** pair than one where both have literals, and `min` says so. Multiplication would make a pair with one strong and one weak side weaker than either side's own confidence — plausible in a strict probabilistic model, but harder to read, and the empirical difference from `min` is small. `min` is the choice; a future ADR can revisit if the corpora argue for a different combine.

### Why weak groups exist, and why they are not in the default

A link with `identity_confidence` 0.4 is a **real** signal — the writer's literal names a store, the reader's parameter **may** point at it — and it is **not** a **strong** signal — the reader's parameter might point at a different store. Dropping it (a single threshold at 0.7) loses information the AST has. Including it in the default (a single threshold at 0.3) floods the enumeration with possible pairs, and ADR-0012's default is a selection, not a dump.

The two-level threshold and `include_weak=True` make the choice explicit: the default is the strong set, the weak set is one flag away, and a weak group carries `weak: true` so the LLM and the report see why its confidence is lower. The precedent is B.4b: a signal that reaches the model with its uncertainty named is more honest than a signal the model never sees, and more honest than a signal the model is asked to treat as certainty.

## Consequences

- **`store` is a node kind.** `VALID_NODE_KINDS` and the schema's CHECK gain it. One node per `(family, identity_hint)` the scan sees a literal for.
- **`writes_to` targets a `store`**, for every family. B.2's `writes_to → untrusted_source` is migrated in B.3c.
- **`reads_from` is a new edge kind**, `store → untrusted_source`, structural, `observed_by = ["ast"]`, `data_flow_confirmed = NULL`.
- **`STRUCTURAL_EDGE_KINDS` grows** to `{"guards", "writes_to", "reads_from"}`.
- **`Edge.identity_confidence` is a new field**, `NULL` everywhere except `writes_to` and `reads_from`. `upsert` combines it by `1 − (1 − old)(1 − new)` for those two kinds and by `max` otherwise.
- **`find_chain_groups` joins by store id**, with the anchor being the store, not the `untrusted_source`. `find_chains` is unchanged.
- **Weak groups** (`0.3 ≤ join confidence < 0.7`) are in the graph, `weak: true`, not in the default enumeration; `include_weak=True` includes them.
- **`store_confidence_threshold`** is `config.yaml`'s, default `0.7`.
- **B.2's write side migrates in B.3c.** B.3a (mechanism) and B.3b (`user_upload`) land first, so the migration runs against a model that already works for one family.
- **Layer 2 is the enrichment point** for `identity_confidence` (Phase C). The field exists; how runtime writes it is a separate decision.

## Revision note (2026-10-29)

§1 originally listed `mcp_catalogue` among the store families and implied that a family is the semantic role of a store. That was wrong. A family is the **technology** (how the store is reached); the semantic role is the **source type** on the read site. The correction matters because `user_upload` — the B.3b family in the original text — is not a family at all: an upload into `/uploads/` and a read from `/uploads/` are a `store('fs', '/uploads/')` pair with `source_type='user_upload'` on the read site. Corrected in §1, with §12 naming the family-module / registry shape as the implementation plan.

The correction was made before any code consumed the original text: B.3a shipped the mechanism with no families, and B.3b-core (the first consumer) starts after this revision. No code is invalidated; the shape ADR-0021 was meant to describe is what the code will implement.

The revision is recorded here, in the header, and in the commit that made it — not folded into the original text silently.
